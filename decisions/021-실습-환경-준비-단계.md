# 021. 실습 환경 준비 단계

- 상태: 채택
- 날짜: 2026-11-19

## 배경

[ADR 016](016-fe-디자인-방향.md)은 화면 검토에서 "환경 준비 중 세부 단계를 학습자에게 보여 줄 수 있게 한다"고 정했다. 지금 학습자가 알 수 있는 준비 상태는 `CREATING`(공간을 만드는 중)과 `INITIALIZING`(시작하는 중) 두 가지다([ADR 012](012-실습-환경-수명-주기.md)).

제약은 다음과 같다.

- 준비 시간은 대부분 `INITIALIZING`에서 쓴다. 테스트 문제는 Ready까지 21초였고, DB가 있는 문제는 DB 초기화를 기다리느라 더 걸린다
- 실습 Pod의 시작 스크립트(Challenge 저장소 `hackforge/entrypoint.sh`, 모든 문제 공통)는 이미 단계마다 `hackforge: <epoch 초> <단계>` 한 줄을 stdout에 남긴다(`start`, `dockerd-ready`, `images-loaded`, `compose-up`)
- 클러스터를 호출하는 곳은 reconciler 하나다(ADR 012). 학습자의 polling이 클러스터 요청으로 이어지면 안 된다
- 학습자는 실습 Pod 안에서 root다(ADR 014)

## 선택지

1. reconciler가 Pod 로그의 단계 기록까지 읽어 4단계로 보여 준다
2. DB 상태와 Pod 상태만으로 3단계(공간, 컨테이너, 서비스)로 보여 준다

## 결정

1로 한다(2026-11-19 사람이 결정).

### 단계

| 단계 | 화면 이름(안) | 판정 |
|---|---|---|
| `SPACE` | 실습 공간 만들기 | 상태가 `CREATING` |
| `CONTAINER` | 컨테이너 시작 | `INITIALIZING`이고 로그에 `dockerd-ready`가 아직 없음. 스케줄링, 이미지 준비, Docker 시작을 포함한다 |
| `LOADING` | 실습 서비스 불러오기 | `dockerd-ready`는 있고 `images-loaded`는 없음 |
| `STARTING` | 서비스 시작과 상태 확인 | `images-loaded`가 있음. compose 서비스가 뜨고 healthcheck를 통과하기를 기다린다 |

- 상태가 `READY`가 되면 준비 완료다. 화면 이름은 fe 화면을 만들 때 [ADR 019](019-화면-문구-말투와-용어.md)에 맞춰 다듬는다
- `compose-up`은 단계를 나누지 않는다. `docker compose up -d`가 끝난 뒤에도 healthcheck를 기다리므로 `STARTING` 안에서 학습자에게 달라지는 것이 없다

### 저장과 읽기

- `lab_sessions.prep_step`(VARCHAR, null 가능)에 저장한다. 세션을 만들 때 `SPACE`, Pod를 만들고 `INITIALIZING`으로 갈 때 `CONTAINER`다
- reconciler는 `INITIALIZING` 세션마다 Pod 로그를 읽어 단계를 정한다. 로그는 처음부터 읽되 크기 상한(`limitBytes`)을 둔다. 시작할 때 남는 로그(dockerd 시작 로그와 단계 기록)는 상한보다 훨씬 작다
- 단계는 앞으로만 간다. 로그 읽기가 실패하거나 기록이 없으면 이전 단계를 그대로 둔다. Ready 판정과 실패 처리는 로그와 상관없이 지금처럼 Pod 상태로 한다
- 재시도(ADR 012)로 `CREATING`에 돌아가면 `SPACE`로 돌아간다
- `READY`, `TERMINATING`, `DELETED`, `FAILED`가 되면 `null`이다

### API

- `LabSessionResponse`에 `prepStep`(`LabPrepStep`, 준비 중이 아니면 `null`)과 `retrying`(재시도 중이면 `true`, `start_attempts`로 판단)을 더한다. `openapi.yaml` 0.4.0
- 단계 순서와 이름은 fe가 가진다. API는 현재 단계만 준다

### 권한

Pod 로그 읽기 권한의 범위는 두 가지를 비교했다.

1. 세션 namespace마다 RoleBinding으로 준다
2. 백엔드 ClusterRole에 `pods/log` `get`을 더한다

1로 한다(2026-11-19 사람이 결정). [ADR 013](013-실습-pod-격리와-백엔드-권한.md) "백엔드 권한"에 다음을 더한다.

- `pods/log` `get`만 가진 ClusterRole `hackforge-lab-log-reader`를 둔다
- 백엔드는 `lab-<세션 id>` namespace를 만들 때 RoleBinding `lab-log-reader`(역할 `hackforge-lab-log-reader`, 대상 `hackforge-backend` service account)도 만든다. namespace를 지우면 같이 지워진다
- 백엔드 ClusterRole에 `rolebindings` `create`와, `resourceNames`를 `hackforge-lab-log-reader` 하나로 좁힌 `clusterroles` `bind`를 더한다. Kubernetes는 자기에게 없는 권한을 담은 RoleBinding을 만들지 못하게 막으므로 `bind`로 이 역할 하나만 허용한다
- ValidatingAdmissionPolicy(`hackforge-backend-lab-only`)에 `rolebindings`를 더해 `lab-` namespace에서만 만들 수 있게 하고, 역할이 `hackforge-lab-log-reader`이고 대상이 `hackforge-backend` 하나인 RoleBinding만 허용한다

## 이유

- 1: 오래 걸리는 구간(서비스 이미지 불러오기, DB 초기화)이 따로 보여야 학습자가 멈춘 것이 아니라 진행 중인 것을 안다. 2는 그 구간이 "서비스 시작" 하나로 묶인다
- 시작 스크립트가 이미 단계 기록을 남기고 있어서 Challenge 이미지는 바꾸지 않는다
- DB에 저장하면 학습자의 polling은 DB만 읽는다. reconciler 주기(3초)만큼 늦게 바뀌지만 단계 하나가 몇 초 이상 걸리므로 화면에서 차이가 없다
- 학습자가 Pod 안에서 가짜 단계 기록을 출력해도 자기 화면의 단계 표시만 바뀐다. 준비 완료는 readinessProbe가 판정한다
- 권한 1: RBAC는 ClusterRole의 권한을 namespace로 좁힐 수 없고, ValidatingAdmissionPolicy는 읽기 요청에 걸리지 않는다. 2로 하면 백엔드 인증 정보가 유출됐을 때 `kube-system` 등 모든 namespace의 Pod 로그(실수로 찍힌 token, 내부 주소, 오류 덤프)가 읽힌다. 1은 로그를 실습 namespace에서만 읽게 하고, 늘어나는 것은 세션마다 API 요청 1번과 수백 byte짜리 오브젝트 1개다. RoleBinding 권한이 반영되기 전에 로그를 읽어 실패해도 이전 단계를 유지하고 다음 주기에 다시 읽는다

## 결과

- 백엔드: migration V9(`lab_sessions.prep_step`), `openapi.yaml` 0.4.0, reconciler가 `INITIALIZING` 세션의 Pod 로그를 읽음, `LabCluster`에 RoleBinding 생성과 로그 읽기 추가
- 인프라: `infra/k8s/`에 ClusterRole `hackforge-lab-log-reader`, 백엔드 ClusterRole의 `rolebindings` `create`와 `bind`, admission policy의 RoleBinding 규칙. 개발 클러스터에 다시 적용한다
- 이미 만들어진 실습 namespace에는 RoleBinding이 없어서 그 세션은 준비 단계가 `CONTAINER`에 머문다. 적용 전에 진행 중 세션을 끝낸다
- Challenge 저장소: 바꾸지 않는다. 시작 스크립트의 단계 기록 형식(`hackforge: <epoch 초> <단계>`)을 바꾸면 백엔드 판정도 같이 바꿔야 한다
- fe 실습 시작 화면은 이 API가 머지된 뒤 별도 이슈로 만든다
