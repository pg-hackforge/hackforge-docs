# 012. 실습 환경 수명 주기: reconcile loop, 상태, 정원, idle 종료

- 상태: 채택
- 날짜: 2026-11-11

## 배경

실습 환경 기능(#6)은 학습자가 실습을 시작하면 전용 환경을 만들고, 학습자가 끝내거나 30분 동안 입력이 없으면 지운다. 실습 환경이 `sysbox-runc` Pod 하나 안의 Docker Compose라는 것은 [ADR 005](005-실습-환경-실행-기반.md)와 [ADR 009](009-sysbox-containerd-설정.md)에서 정했다. 이 ADR은 백엔드가 언제 어떻게 클러스터를 호출하는지, 세션 상태를 어떻게 저장하는지, 동시 정원과 학습자당 1세션을 어떻게 지키는지, idle을 어떻게 판단하는지를 정한다. Pod 격리와 백엔드 권한은 [ADR 013](013-실습-pod-격리와-백엔드-권한.md)에서 정한다.

개발 VM에서 Pod 생성부터 DB healthy까지 27.7초가 걸렸고, 그중 image pull이 20.3초였다(ADR 009). HTTP 요청 하나 안에서 기다리기에는 길다.

## 선택지

생성 요청 처리

1. 요청 안에서 클러스터를 호출하고 환경이 준비될 때까지 기다림
2. 요청은 DB에 `CREATING`으로 넣고 바로 응답. fe는 polling으로 상태를 확인

클러스터를 호출하는 곳

1. API 요청 처리 코드가 바로 호출하고, 백그라운드 작업이 준비 확인과 정리를 이어 감
2. reconcile loop. 요청은 DB에 원하는 상태만 쓰고, 주기적으로 도는 `LabReconciler`만 클러스터를 호출

세션 격리 단위

1. 세션마다 namespace `lab-<세션 id>`
2. namespace 하나에 세션마다 Pod

Challenge 안의 서비스 이미지(nginx, DB 등)

1. Challenge 이미지 안에 tar로 넣고 시작할 때 `docker load`
2. 실습 Pod가 시작할 때 registry에서 pull
3. 클러스터 안에 registry를 두고 pull

동시 정원 확인

1. 시작 트랜잭션에서 PostgreSQL advisory lock을 잡고 진행 중 세션 수를 센 뒤 insert
2. 정원만큼 slot 행을 두고 행 lock

문제 목록 출처

1. 설정 파일(`hackforge.challenges[...]`)
2. `challenges` 테이블. 개발 DB에는 개발 전용 seed로 테스트 문제를 넣음
3. `challenges` 테이블. Flyway migration으로 테스트 문제를 넣음

## 결정

생성 요청은 비동기(2번), 클러스터 호출은 reconcile loop(2번), 격리는 세션마다 namespace(1번), 서비스 이미지는 tar(1번), 정원은 advisory lock(1번), 문제 목록은 테이블과 개발 전용 seed(2번)로 한다.

### 처리 흐름

- `POST /api/labs`는 승인 상태를 DB에서 읽고, 정원과 학습자당 1세션을 확인한 뒤 `CREATING` 행을 넣고 202로 응답함
- `DELETE /api/labs/{id}`는 상태를 `TERMINATING`으로 바꾸고 202로 응답함. 생성 중(`CREATING`, `INITIALIZING`)에도 종료할 수 있음
- `LabReconciler`가 몇 초마다 진행 중인 세션을 읽어 한 단계씩 진행함. 클러스터를 호출하는 곳은 여기뿐임

| 상태 | reconciler가 하는 일 | 다음 상태 |
|---|---|---|
| `CREATING` | namespace, NetworkPolicy, ResourceQuota, Pod 순서로 생성(ADR 013). 이미 있으면 건너뛰고, 이전 Pod가 삭제 중이면 다음 주기에 다시 봄 | `INITIALIZING` |
| `INITIALIZING` | Pod가 Ready면 진행. Pod `Failed`, image pull 실패, `start-timeout` 초과면 실패 처리 | `READY`. 첫 실패는 Pod만 삭제하고 `CREATING`(재시도 1회), 두 번째 실패는 `TERMINATING` |
| `READY` | Pod가 `Failed`이거나 없으면 종료 처리 | `TERMINATING`(`POD_LOST`) |
| `TERMINATING` | namespace 삭제. 삭제가 끝날 때까지 기다림 | `DELETED`. 시작 실패로 온 세션은 `FAILED` |

- 각 단계는 멱등하게 만듦. 생성할 때 `AlreadyExists`, 삭제할 때 `NotFound`는 성공으로 처리함. 백엔드가 재시작해도 DB 상태에서 이어서 진행함
- 세션 하나에서 예외가 나면 로그를 남기고 다음 세션을 처리함. 실패한 세션은 다음 주기에 재시도함
- idle 검사는 reconcile 주기마다 `READY` 세션을 볼 때 함(2026-11-12 결정, 처음에는 1분마다). orphan 정리는 백엔드가 시작할 때와 몇 분마다 함
  - label `hackforge/lab=true`인 namespace 중 DB에 진행 중인 세션이 없는 것은 삭제함
  - `READY`인데 namespace나 Pod가 없는 세션은 `POD_LOST`로 종료함
  - DB 행이 namespace보다 먼저 생기므로 생성 중인 namespace를 잘못 지우지 않음
- 상태가 바뀔 때마다 세션 id, 사용자 id, 이전 상태, 다음 상태, 사유를 로그로 남김
- 백엔드는 v1에서 인스턴스 하나로 운영함

### 상태와 종료 사유

```
CREATING ──▶ INITIALIZING ──▶ READY ──▶ TERMINATING ──▶ DELETED
   ▲              │                          ▲
   └── 재시도 1회 ─┤                          │
                  └── 두 번째 실패 ──▶ TERMINATING ──▶ FAILED
```

- 끝난 상태는 `DELETED`와 `FAILED` 둘임. 나머지는 모두 진행 중 세션으로 보고, 학습자당 1세션과 동시 정원에 포함함. `TERMINATING`도 namespace 삭제가 끝날 때까지 포함함
- `end_reason`: `USER`(학습자 종료), `IDLE`, `POD_LOST`. `FAILED`는 상태로 구분하므로 사유를 따로 두지 않음
- 관리자 강제 종료(`ADMIN`)와 상태 전이 기록(SessionEvent)은 #13(관리와 기록: 세션 목록, 강제 종료, 기록 조회, 관측성 대시보드)에서 추가함
- 공격, 방어 단계 상태(`OFFENSIVE` 등)는 #8(공격 대상 화면과 웹 터미널) 이후에 추가함. 상태 컬럼 길이는 기획서 상태 중 가장 긴 `ATTACK_VERIFIED`(15자)에 맞춤

### 데이터

`challenges`

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT identity PK | API와 FK에서 씀 |
| `slug` | VARCHAR(50) UNIQUE | 사람이 읽는 이름. seed, runbook, 로그에서 씀. 소문자, 숫자, `-` |
| `title` | VARCHAR(100) | 문제 목록에 보이는 이름 |
| `image` | VARCHAR(255) | 지금 쓰는 Challenge 이미지(태그 포함) |
| `created_at` | TIMESTAMPTZ | |

`lab_sessions`

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT identity PK | namespace 이름 `lab-<id>` |
| `user_id` | BIGINT FK `users`, `ON DELETE CASCADE` | |
| `challenge_id` | BIGINT FK `challenges`, `ON DELETE RESTRICT` | |
| `image` | VARCHAR(255) | 시작할 때의 Challenge 이미지. 재시도 Pod도 이 값으로 만듦 |
| `status` | VARCHAR(15) CHECK | 위 6개 |
| `end_reason` | VARCHAR(15) CHECK, null | `USER`, `IDLE`, `POD_LOST` |
| `start_attempts` | SMALLINT | 재시도 판단 |
| `status_changed_at` | TIMESTAMPTZ | `start-timeout` 계산 |
| `last_activity_at` | TIMESTAMPTZ, null | `READY`가 될 때 채움 |
| `created_at`, `ready_at`, `ended_at` | TIMESTAMPTZ | `ready_at`, `ended_at`은 null 가능 |

- 학습자당 1세션: `user_id`에 partial unique index(`WHERE status NOT IN ('DELETED', 'FAILED')`)
- reconciler 조회용: `status`에 같은 조건의 partial index
- 개발 seed는 `src/main/resources/db/dev/R__dev_challenges.sql`에 두고, `bootRun`에서만 Flyway location에 `classpath:db/dev`를 추가함. 테스트는 테스트 코드가 직접 넣음
- 프로그램 사이에서는 id로, 사람이 보는 곳에서는 slug로 문제를 가리킴. `POST /api/labs`도 `challengeId`를 받음

### 정원과 학습자당 1세션

- 시작 트랜잭션에서 `pg_advisory_xact_lock(<고정 key>)`을 잡고 진행 중 세션 수를 센 뒤 insert함. `hackforge.lab.max-concurrent` 이상이면 503 `LAB_CAPACITY_FULL`
- 같은 학습자의 진행 중 세션이 있으면 409 `LAB_ALREADY_ACTIVE`. 코드 검사를 동시에 통과해도 partial unique index가 막음
- 승인되지 않은 계정이면 403 `ACCOUNT_NOT_APPROVED`. 승인 상태는 세션이 아니라 매번 DB에서 읽음([ADR 011](011-계정-규칙.md))

### idle 종료

- `READY`가 되는 시각을 `last_activity_at`의 시작값으로 씀. 생성 중에는 idle 시간을 세지 않음
- #6에서 활동 입력은 `POST /api/labs/{id}/activity`([계속하기]) 하나이고, 받으면 바로 DB에 씀. 응답으로 새 `idleDeadline`, `idleWarningAt`을 줌
- 웹 터미널, Target으로 가는 요청(#8 공격 대상 화면과 웹 터미널), 웹 IDE(#10 방어: 웹 IDE, 재빌드·재배포, 초기화)가 생기면 같은 기록 경로를 호출함. 그때 활동을 메모리에 모아 세션당 1분에 한 번만 DB에 쓰는 `ActivityTracker`를 추가하고, idle 판단은 DB 값과 메모리 값 중 최근 값으로 함
- fe의 상태 polling(`GET`)은 활동으로 세지 않음
- reconciler가 reconcile 주기마다 `READY`이고 `last_activity_at`이 `idle-timeout`보다 오래된 세션을 `TERMINATING`(`IDLE`)으로 바꿈. 세션마다 타이머를 두지 않으므로 백엔드 재시작에 영향받지 않음
- 세션 응답의 `idleDeadline`, `idleWarningAt`은 `READY`일 때만 줌. fe는 `idleWarningAt`부터 "5분 뒤 종료됩니다 [계속하기]"를 띄움

### Challenge 이미지

- Challenge 이미지 안에 서비스 이미지를 `docker save`로 묶은 tar를 넣고, 시작할 때 `docker load` 후 `docker compose up`함. 실습 Pod는 외부 통신이 없음
- 이미지는 `/hackforge/entrypoint.sh`(dockerd 시작, load, compose up)와 `/hackforge/ready.sh`(모든 서비스가 healthy면 성공)를 가짐. Pod readinessProbe가 `ready.sh`를 실행함
- 개발 VM에는 registry 없이 넣음. Windows에서 빌드해 `docker save`로 만든 파일을 VM에서 `ctr -n k8s.io images import`로 등록하고, Pod는 `imagePullPolicy: IfNotPresent`와 `latest`가 아닌 태그를 씀
- 미정(결정 필요): 운영 서버에 Challenge 이미지를 넣는 방법(private registry와 pull secret, 또는 같은 import). 운영 서버 구성 때 정함

### API

| 요청 | 성공 | 오류 |
|---|---|---|
| `GET /api/challenges` | 200 `[{id, slug, title}]` | |
| `POST /api/labs` `{challengeId}` | 202 세션 | 403 `ACCOUNT_NOT_APPROVED`, 404 `CHALLENGE_NOT_FOUND`, 409 `LAB_ALREADY_ACTIVE`, 503 `LAB_CAPACITY_FULL` |
| `GET /api/labs/current` | 200 진행 중 세션, 없으면 204 | |
| `GET /api/labs/{id}` | 200 세션 | 404 `LAB_NOT_FOUND` |
| `DELETE /api/labs/{id}` | 202 세션. 이미 종료 중이거나 끝났으면 그 상태 그대로 | 404 `LAB_NOT_FOUND` |
| `POST /api/labs/{id}/activity` | 200 세션 | 404 `LAB_NOT_FOUND`, 409 `LAB_NOT_READY` |

- 세션 응답: `id`, `challengeId`, `challengeTitle`, `status`, `endReason`, `createdAt`, `readyAt`, `endedAt`, `idleDeadline`, `idleWarningAt`. namespace, Pod 이름 같은 클러스터 정보는 넣지 않음
- 남의 세션 id는 404로 응답함. 그 id의 세션이 있다는 것도 알리지 않음
- `GET /api/challenges`는 승인 대기 계정도 호출할 수 있음. 승인은 시작할 때만 확인함
- fe는 생성 중과 종료 중에 2~3초, `READY`일 때 10초 정도 간격으로 `GET /api/labs/{id}`를 polling하고, `DELETED`나 `FAILED`가 되면 멈춤. `FAILED`면 "환경을 만들지 못했습니다"와 다시 시작 버튼을 보여 주고, 다시 시작은 새 세션을 만듦

### 설정값

| 키 | 값 |
|---|---|
| `hackforge.lab.max-concurrent` | 5. 개발 VM은 2(2026-11-12 결정, 세션당 CPU 500m 기준) |
| `hackforge.lab.idle-timeout` | 30m |
| `hackforge.lab.idle-warning` | 5m (종료 몇 분 전에 경고할지) |
| `hackforge.lab.start-timeout` | 5m로 시작. 미정(실측 후 결정): 운영 서버에서 첫 Challenge 생성 시간을 잰 뒤 정함([ADR 006](006-개발-VM과-운영-서버.md)) |
| `hackforge.lab.cpu`, `memory`, `disk` | ADR 013 |
| `hackforge.lab.kubeconfig` | 파일 경로. 비어 있으면 in-cluster 설정(ADR 013) |
| `hackforge.lab.reconcile-interval` | 3s. 앞 실행이 끝난 뒤부터 셈 |
| `hackforge.lab.orphan-cleanup-interval` | 5m |

## 이유

- 생성에 수십 초가 걸려서 요청 안에서 기다리면 연결이 끊기거나 재시도될 때 상태가 꼬임. 비동기로 두면 요청은 짧고, 진행 상황은 DB 상태로 확인할 수 있음
- reconcile loop는 클러스터를 호출하는 곳이 하나라서 생성, 재시도, 종료, idle 종료, orphan 정리가 같은 방식으로 처리됨. 상태가 모두 DB에 있어서 백엔드가 재시작해도 이어서 진행하고, 클러스터 장애가 API 응답에 영향을 주지 않음. Kubernetes controller와 같은 방식임
- namespace를 세션마다 두면 NetworkPolicy, ResourceQuota, Pod Security Admission을 세션 단위로 걸 수 있고, 정리는 namespace 삭제 한 번이면 됨. 코드는 `lab-` namespace만 삭제함
- tar로 넣으면 ADR 009 측정의 image pull 20.3초 대부분이 없어지고, 실습 Pod가 registry에 접속할 필요가 없어 외부 통신을 모두 막을 수 있음. 대신 Challenge 이미지가 커짐
- advisory lock은 count와 insert 사이의 경쟁을 막고 트랜잭션이 끝나면 자동으로 풀림. slot 행을 따로 관리할 필요가 없음
- 학습자당 1세션은 product.md대로 DB constraint로 보장함
- idle 판단을 주기적 조회로 하면 세션마다 타이머를 다시 걸 필요가 없고 재시작에도 안전함. 늦어도 reconcile 주기(3초)만큼만 늦게 종료됨. reconciler가 어차피 주기마다 `READY` 세션의 Pod를 확인하므로 idle 검사를 따로 돌리지 않음
- 1분 throttle은 터미널 입력처럼 활동이 자주 들어올 때를 위한 것이라, 활동 입력이 [계속하기] 하나인 #6에서는 만들지 않음
- `challenges` 테이블을 지금 만들면 `lab_sessions`가 처음부터 FK로 문제를 가리키고, #7(Challenge 형식과 첫 문제(SQLi))은 컬럼을 추가하기만 하면 됨. migration으로 테스트 문제를 넣으면 운영 DB에도 들어가서 3번은 택하지 않음
- 세션에 이미지를 따로 저장하면 문제 이미지가 바뀌어도 재시도와 기록이 시작할 때의 버전을 가리킴

## 결과

- `lab_sessions`가 `users`를 참조하게 된다. 탈퇴로 `users` 행을 지우면 세션 행도 지워지고, 남은 namespace는 orphan 정리가 지운다. [계정 운영 runbook](../infra/account-operations.md)은 migration 작업 때 고친다.
- 종료 직후 새 세션을 시작하면 namespace 삭제가 끝날 때까지 `LAB_ALREADY_ACTIVE`가 난다. fe는 이 동안 "종료 중"을 보여 준다.
- 백엔드를 여러 인스턴스로 늘리면 reconciler가 중복 실행된다. 그때 reconciler 하나만 돌도록 DB lock을 추가한다. 30명 설계 문서에 넣는다.
- 문제가 늘어 Challenge 이미지가 커지면 공통 base 이미지를 분리하고, 그다음 클러스터 안 registry를 검토한다. 30명 설계 문서에 넣는다.
