# 028. 문제 목록 정렬 반대 방향

- 상태: 채택
- 날짜: 2026-11-22

## 배경

문제 목록은 정렬 드롭다운(새로 추가된 순, 쉬운 순, 짧은 순)으로 정렬한다([ADR 020](020-문제-정보와-목록-API.md), 확정 캡처 `main-problems-*`). 화면을 만든 뒤 검토에서, 표 모양 목록이라 열 제목을 눌러 정렬하는 편이 낫지 않냐는 의견이 나왔다(hackforge-fe #20 검토).

조사한 내용은 다음과 같다.

- 데이터 표 화면은 열 제목을 눌러 정렬하는 것이 기본 패턴이다. 정렬할 수 있는 열 제목은 버튼으로 두고 지금 정렬과 방향을 표시한다(Chrome 웹 UI 가이드, W3C APG sortable table)
- 정렬 기준이 화면의 열과 맞지 않으면 드롭다운이 낫다(GitLab 이슈 논의). 문제 목록의 정렬 기준(추가 순서, 난이도, 예상 시간)은 모두 열(번호, 난이도, 예상)과 맞는다
- 지금 API는 기준마다 방향이 하나라 "어려운 순", "긴 순", "오래된 순"을 못 한다

## 선택지

1. 드롭다운 그대로(기본 방향 3개)
2. 열 제목 정렬(번호, 난이도, 예상), 드롭다운 없앰, API에 반대 방향
3. 둘 다
4. 드롭다운 하나에 반대 방향까지 6개(검색 칸 오른쪽), API에 반대 방향

## 결정

4로 한다(2026-11-22 사람이 결정). 처음에는 2로 정해 fe #20에 만들어 보았는데, 화면에서 거르기(왼쪽 필터), 검색(위), 정렬(표 머리)이 세 곳으로 흩어지고, 분류는 필터에 있는데 표 머리에서는 못 누르는 것이 헷갈렸다. 다른 서비스들이 주로 쓰는 방식(목록 위 오른쪽 정렬 드롭다운)으로 바꿨다.

- 검색 칸 오른쪽에 정렬 드롭다운 하나: 새로 추가된 순(기본), 오래된 순, 쉬운 순, 어려운 순, 짧은 순, 긴 순. 고르면 메뉴가 닫힌다
- 열 제목은 누르지 않는 글자다
- `GET /api/challenges`에 `reverse`(boolean, 기본 false)를 더한다. true면 그 정렬의 반대 방향이다. 동점은 반대 방향이어도 새로 추가된 순이다. ADR 020의 정렬 값(`NEWEST`, `DIFFICULTY`, `TIME`)은 그대로 쓴다

## 이유

- 문제 목록은 업무용 표라기보다 학습자가 풀 문제를 고르는 카탈로그에 가깝다. 쇼핑몰과 문제 풀이 사이트(프로그래머스, solved.ac 등)는 거르기와 정렬을 목록 바깥에 두고 정렬은 목록 위 드롭다운이나 탭으로 한다
- 조작(필터, 검색, 정렬)은 목록 바깥, 결과는 표로 나뉘어 덜 헷갈린다
- 문제가 수백 개로 늘면 어려운 문제나 긴 문제부터 보는 일이 생긴다

## 결과

- 백엔드: `openapi.yaml`에 `reverse`, 정렬 SQL에 반대 방향
- fe: 정렬 드롭다운 6개(hackforge-fe #20에 반영), `DESIGN.md`에 적는다
