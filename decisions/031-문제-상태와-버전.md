# 031. 문제 상태와 버전

- 상태: 채택
- 날짜: 2026-11-27

## 배경

v1 문제는 2~3개라, 앞으로 만들 문제를 목록에 "(예정)"으로 미리 보이고 싶다는 요청이 나왔다(2026-11-26). 지금은 `challenges`에 있는 문제는 모두 학습자 목록에 보이고 실습을 시작할 수 있어, 예정 문제를 넣으면 시작했을 때 실습 환경이 뜨지 않는다.

같은 논의에서 나중에 출제 기능을 만들면 문제가 바로 공개되지 않고 심사를 거쳐야 한다는 점도 나왔다. 상태를 예정 하나만 더하지 말고 출제·심사까지 담을 수 있게 설계하기로 했다.

설계하면서 지금 구조의 문제를 하나 찾았다. 실습 세션은 시작할 때 문제 이미지(`lab_sessions.image`)만 고정하고, 공격 검증·방어 검증 스크립트, 힌트, 해답은 검증할 때마다 `challenges`에서 읽는다. `register.sh`는 같은 slug면 내용을 덮어쓰므로, 진행 중 세션이 있을 때 다시 등록하면 그 세션은 옛 이미지와 새 스크립트로 검증받는다.

## 선택지

v1에서 예정 문제를 막는 방법

1. 빈 문제를 등록: "준비 중" 화면만 있는 문제를 제목에 "(예정)"을 붙여 등록. 코드 수정 없음. 시작하면 실제 Pod가 뜨고, 항상 실패하는 검증 스크립트가 필요하고, 추천과 새 문제 표시에 섞임
2. 빈 문제 + fe만 수정: 제목이 "(예정)"으로 시작하면 시작 버튼을 숨김. 백엔드는 시작을 막지 않고, 분류별 개수에 예정 문제가 들어감
3. 문제 상태 칸을 미리 두고 값은 예정과 공개 둘만 씀: 백엔드가 시작을 거절하고 개수·추천에서 뺌. v1.2 문제 상태의 일부라 버리지 않음

문제 상태 구조

1. `challenges`에 상태 칸 하나
2. 문제와 문제 버전을 나누고 상태를 둘로(문제 상태, 버전 상태)

## 결정

v1은 선택지 3, 구조는 선택지 2로 하고, 구조 전체는 v1.2에 만든다(2026-11-27 사람이 결정). v1의 세부 3개(예정 문제 목록 위치, 공개 시각, 예정 문제 상세)는 AI 추천대로 정했다(2026-11-27 사람이 결정).

### v1: 문제 상태 두 값

- `challenges.status`: `PLANNED`(예정), `PUBLISHED`(공개). 기본 `PUBLISHED`이고 지금 문제는 모두 `PUBLISHED`
- 예정 문제는 목록 정보(slug, 제목, 요약, 분류, 난이도, 예상 시간)만 있고 이미지, 설명, 스크립트, 해답, 힌트가 없다. 이 칸들은 비울 수 있게 하되 `PUBLISHED`면 비울 수 없게 DB 제약을 건다
- 예정 문제는 backend migration으로 넣는다. 분류 목록([ADR 020](020-문제-정보와-목록-API.md))처럼 목록을 바꾸려면 be PR을 올린다
- 같은 slug로 `register.sh`를 실행하면 내용을 채우고 `PUBLISHED`로 바꾼다(template과 문제 저장소의 `register.sh`)
- 백엔드
  - 예정 문제의 실습 시작은 409로 거절
  - 분류별·난이도별 개수(`facets`)에서 뺌
  - 새 문제 표시(`isNew`), 홈 추천과 내 기록 분석의 추천, 진행 요약에서 뺌
  - 목록·상세 응답에 `status`
- fe: 제목 앞에 "(예정)", 시작 버튼 자리에 "준비 중이에요"
- 진행 중 세션이 있는 문제는 다시 등록하지 않는다. 운영 runbook에 적는다(v1.2 버전 분리로 해결)
- 예정 문제는 어느 정렬이든 공개 문제 뒤에 온다. 새로 추가된 순이면 migration으로 넣은 예정 문제가 맨 위에 오기 때문이다
- `challenges.published_at`(처음 `PUBLISHED`가 된 시각)을 더하고 `isNew`와 새로 추가된 순을 이 시각으로 계산한다. `created_at` 기준이면 예정이던 문제가 공개돼도 migration 시각으로 계산돼 새 문제 표시가 안 붙고 공개 순서와 다르게 정렬된다. 지금 문제는 `created_at`과 같게 채운다. v1.2의 공개·내림에도 쓴다
- 예정 문제 상세 패널에는 요약과 "준비 중이에요"를 보인다

### v1.2: 문제와 버전 분리

- `challenges`(문제): slug, 분류, 제목, 요약, 난이도, 예상 시간, 문제 상태
- `challenge_versions`(문제 버전, 새 테이블): 이미지, 설명, 스크립트, 힌트, 해답, 수정 불가 파일, 버전 상태
- 공개 중인 문제를 고칠 때는 새 버전을 만들고, 새 버전이 심사받는 동안 학습자는 공개 중 버전으로 실습한다
- 실습 세션은 시작할 때 버전 하나에 고정되고 검증, 힌트, 해답을 그 버전에서 읽는다

문제 상태

| 상태 | 학습자 목록 | 실습 시작 |
|---|---|---|
| `PRIVATE` 비공개 | 안 보임 | 관리자·출제자 미리 보기만 |
| `PLANNED` 예정 | "(예정)"으로 보임 | 못 함 |
| `PUBLISHED` 공개 | 보임 | 누구나 |
| `RETIRED` 내림 | 안 보임 | 못 함. 지난 실습 기록과 연 해답은 다시 볼 수 있음 |

버전 상태: `DRAFT` 작성 중 → 제출 → `IN_REVIEW` 심사 중 → `APPROVED` 승인 또는 `CHANGES_REQUESTED` 수정 요청(다시 작성 중으로). 승인된 버전을 공개하면 `PUBLISHED` 공개 중이 되고, 그 전 공개 중 버전은 `SUPERSEDED` 이전 버전이 된다.

범위는 네 단위이고 모두 v1.2에 한다.

| 단위 | 내용 |
|---|---|
| A | 문제·버전 분리, 두 상태, 상태 기록(`challenge_events`: 누가, 언제, 어디서 어디로, 사유), 기존 기능 반영(목록, 시작, 새 문제 표시는 공개 시각, 추천·분석·진행 요약은 공개 문제만, `register.sh`는 새 버전 올리기), 학습자 화면(예정·내린 문제 안내) |
| B | 관리자 [문제] 탭: 상태별 목록, 버전 기록, 심사(승인, 사유를 적은 수정 요청), 공개, 예정 전환, 내림, 심사용 미리 보기 실습 |
| C | 제출 때 자동 검사: 실습 Pod에서 원본에 공격이 통하는지, 원본이 정상 기능 테스트를 통과하는지, 해답대로 고치면 공격이 막히고 정상 기능 테스트를 통과하는지 |
| D | 출제자(`AUTHOR`) 화면과 권한: 내 문제, 버전 올리기와 제출, 받은 심사 의견. 출제자는 자기 문제를 승인할 수 없다 |

- 예정 문제는 분류별 개수에 넣지 않는다(v1과 같음)
- 문제마다 여러 언어로 구현을 두는 것(학습자가 언어를 고름)은 v1.2 설계 때 함께 설계한다. 버전 아래 언어별 구현 단계가 생기는 구조이고, 공격 쪽(`exploit.sh`, `functional-test.sh`, 공격 힌트, 공격 성공 판정)은 언어끼리 같은 HTTP 동작을 하게 만들어 함께 쓴다(2026-11-27 사람이 결정)
- 미정(결정 필요): 언어별 구현을 v1.2에 만들지 그 뒤에 만들지(v1.2 설계 때 정함)
- 미리 보기 실습은 학습자 기록, 통계, 관리자 세션 목록의 학습자 실습과 섞이지 않게 표시한다
- 미정(결정 필요): 예약 공개, 심사자 역할을 관리자와 나눌지, 내릴 때 진행 중 세션 처리(끝까지 둘지, 종료할지)
- 미정(결정 필요): D와 [product.md](../product.md) "이번에 안 할 것"의 문제 등록 파이프라인(업로드 → CI 빌드·SBOM·취약점 스캔 → registry)의 관계

## 이유

- v1에서 상태 칸을 미리 두면 백엔드가 시작을 막고 개수·추천에서 빼므로, 화면을 거치지 않는 요청이나 서버가 세는 값까지 맞는다. 값만 v1.2의 일부라 v1.2에서 다시 만들지 않는다
- 문제와 버전을 나누면 공개 중인 문제를 고치는 동안에도 학습자 실습이 끊기지 않고, 진행 중 세션의 검증이 다른 버전과 섞이지 않는다. 심사는 버전 단위로 하고 공개 여부는 문제 단위로 보는 것이 출제·심사가 있는 서비스의 일반 구조다
- 상태가 바뀐 기록을 남겨야 심사 의견과 공개·내림 이유를 나중에 확인할 수 있다

## 결과

- v1.2: 시작할 때 이 ADR의 A~D로 작업 목록을 쓴다

## 정정

- 2026-11-27: 필터 개수(분류별·난이도별·내 상태별, API의 `facets`)에 예정 문제도 센다(hackforge-be #73 리뷰에서 사람이 결정). 예정 문제는 목록에 보이는데 개수에서 빼면 필터 옆 숫자와 목록 줄 수가 달라진다. 홈 내 진행과 내 기록 분석의 전체·분류별 문제 수는 그대로 공개 문제만 센다
- 2026-11-27: "D와 문제 등록 파이프라인의 관계" 미정의 방향을 정했다(사람이 결정). 출제자는 template을 fork해 개발하고 저장소 링크로 제출하며, 서버가 제출 시점 commit을 가져와 `meta/` 형식(ADR 014)을 검사하고 격리된 환경에서 빌드·스캔·`check.sh`를 돌린 뒤 문제 버전(작성 중 → 심사 중)으로 넣는다. `register.sh`의 검사 규칙은 백엔드로 옮기고, 관리자가 DB에 직접 넣는 부분은 심사 흐름으로 바뀐다. v1은 관리자가 `register.sh`로 등록한다. 비공개 저장소 접근, 빌드 격리, 넣을 버전은 v1.2 설계 때 정한다([roadmap.md](../roadmap.md) "그 뒤")
