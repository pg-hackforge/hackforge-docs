# 011. 계정 규칙: 가입 정보, 승인, 역할, 잠금, 단계별 도입

- 상태: 채택
- 날짜: 2026-11-04

## 배경

product.md는 "자가 가입 또는 외부 로그인(GitHub, Google), 관리자 승인 후 사용"만 정했다. 계정 기능(#12)을 만들려면 무엇으로 사람을 구분하는지, 무엇을 받는지, 첫 관리자는 어떻게 생기는지, 비밀번호를 잊으면 어떻게 하는지를 정해야 한다. 인증 방식(서버 세션 + 쿠키)은 [ADR 002](002-인증-방식.md)에서 정했다.

## 선택지

도입 범위

1. v1에 자가 가입, 이메일 인증, GitHub·Google 로그인을 모두 넣는다.
2. v1은 자가 가입만, 이메일 인증·비밀번호 재설정은 v1.1, GitHub·Google 로그인은 v1.2에 넣는다.

계정 구분

1. 로그인 방식마다 별개 계정 (`(방식, 그 방식의 사용자 ID)`로 구분)
2. 한 사람 = 계정 하나 (이메일이 모든 방식을 통틀어 유일)

첫 관리자

1. 가입한 뒤 DB에서 직접 승격
2. 앱 시작 때 환경변수의 이메일·비밀번호로 생성
3. 첫 가입자를 관리자로

## 결정

### 단계별 도입

- **v1:** 자가 가입(이메일 + 비밀번호)만 둔다.
- **v1.1:** 이메일 인증과 메일로 비밀번호 재설정을 넣는다.
- **v1.2:** GitHub·Google 로그인을 넣는다. OAuth 인증 뒤 추가 정보 화면에서 가입을 마무리한다.

### 가입 정보 (모든 가입 방식 공통)

| 항목 | 규칙 |
|---|---|
| 이메일 | 로그인 아이디. 모든 가입 방식을 통틀어 유일, 소문자로 저장 |
| 비밀번호 | 8~64자, 영문·숫자·특수문자를 각각 하나 이상. bcrypt로 해시 |
| 이름 | 필수, 50자까지 |
| 닉네임 | 필수, 유일, 2~20자, 한글·영문·숫자·`_` |
| 소속 | 필수, 100자까지 자유 입력(학교·학과·회사 등) |
| 가입 메모 | 선택, 200자까지. 관리자가 본인을 확인하는 데 쓴다(예: "OO교수님 웹보안 3분반") |
| 개인정보 수집·이용 동의 | 필수. 동의 시각을 저장한다 |

휴대폰 번호·생년월일 등은 받지 않는다. 쓸 곳이 없는 개인정보는 받지 않는다(최소 수집).

### 승인과 역할

- 가입하면 상태는 `PENDING`(승인 대기), 역할은 `LEARNER`(학습자)다.
- 상태는 `PENDING → APPROVED`, `PENDING → REJECTED`, `REJECTED → APPROVED`로만 바뀐다. 계정 정지는 v1 범위 밖이라 `APPROVED`에서 다른 상태로 가지 않는다.
- 대기·거절 계정도 로그인할 수 있다. 화면은 상태를 보고 "승인 대기 중"·"거절됨"을 안내하고, 실습 시작만 막는다. 재신청 버튼은 없다.
- 역할은 `LEARNER` / `AUTHOR`(출제자) / `ADMIN`. 관리자는 역할 변경 API로 언제든 바꾼다. 자기 자신의 역할은 바꿀 수 없다. 역할이 바뀐 계정의 로그인 세션은 모두 지운다.
- 첫 관리자는 평소처럼 가입한 뒤 서버에서 psql로 역할을 `ADMIN`, 상태를 `APPROVED`로 바꾼다. 절차는 `infra/`에 둔다.

### 로그인과 세션

- 같은 계정으로 5번 연속 실패하면 15분 잠근다. 잠긴 동안은 비밀번호를 확인하지 않고 거절한다. 성공하면 실패 횟수를 0으로 되돌린다.
- 이메일이 틀렸는지 비밀번호가 틀렸는지 구분하지 않고 같은 문구로 거절한다.
- 로그인 세션은 요청이 없으면 30분 뒤 만료된다. 같은 계정으로 여러 곳에서 동시에 로그인할 수 있다.
- 세션에는 사용자 id와 역할만 둔다. 세션의 사용자 이름(principal name)은 사용자 id다.

### 비밀번호 분실과 탈퇴 (v1)

- 비밀번호를 잊으면 관리자가 임시 비밀번호를 발급한다. 임시 비밀번호는 응답으로 관리자에게 한 번만 보이고, 관리자가 직접 전달한다. 발급하면 그 계정의 로그인 세션을 모두 지우고 잠금을 푼다.
- 로그인한 사용자는 현재 비밀번호를 확인한 뒤 비밀번호를 바꿀 수 있다. 바꾸면 지금 세션을 뺀 나머지 세션을 지운다.
- 탈퇴(개인정보 삭제)는 관리자에게 요청하고, 관리자가 `infra/`의 절차대로 처리한다. 탈퇴 API는 실습 기록(#13)을 탈퇴 뒤 어떻게 남길지 정할 때 만든다.

## 이유

- 도입 순서: 이메일 인증 없이 "이메일 전체 유일"과 OAuth를 함께 두면, 남의 이메일로 먼저 자가 가입해 진짜 주인의 GitHub·Google 가입을 막을 수 있다. 인증이 먼저 들어가면 미인증 계정은 효력이 없다. v1은 모든 가입을 관리자가 승인하므로, 관리자가 이름·소속·메모로 확인하는 것이 인증을 대신한다.
- 한 사람 = 계정 하나: 로그인 방식마다 계정이 따로면 한 사람이 실습 세션을 둘 띄울 수 있다. 그러면 "학습자당 세션 1개"와 동시 정원이 사람 기준으로 지켜지지 않는다.
- DB 직접 승격: 코드가 없고, 설정에 관리자 비밀번호를 둘 일이 없다. 첫 가입자를 관리자로 하면 서버를 열자마자 다른 사람이 먼저 가입할 수 있다.
- 자기 역할 변경 금지: 관리자가 자기 역할을 내리지 못하므로 관리자는 항상 한 명 이상 남는다.
- 역할 변경 때 세션 삭제: 역할은 로그인할 때 세션에 들어간다. 지우지 않으면 권한을 빼도 로그아웃할 때까지 예전 권한이 남는다. Spring Session JDBC는 사용자 이름으로 세션을 찾을 수 있다.
- 로그인 30분: Spring 기본값이고, OWASP 세션 관리 권고가 일반 서비스에 제시하는 범위(15~30분)다. 요청이 있을 때마다 연장된다.
- 비밀번호 길이 상한 64자: bcrypt는 72바이트까지만 읽는다.

## 결과

- v1 `users` 테이블에는 로그인 방식 컬럼이 없고 비밀번호 해시는 필수다. v1.1(이메일 인증 상태, 메일 토큰 테이블), v1.2(로그인 방식, OAuth 사용자 ID, 비밀번호 해시 선택)는 Flyway 마이그레이션으로 더한다.
- v1.1에서 정할 것: v1에서 이미 승인된(미인증) 계정에 인증을 요구할지, 관리자 승인을 인증으로 볼지
- v1.2에서 정할 것: 한 계정에 로그인 방식을 여러 개 연결하는 기능. 그 전까지는 이미 가입된 이메일로 다른 방식의 가입을 시도하면 원래 방식으로 로그인하라고 안내한다.
- 승인 상태는 세션에 담지 않으므로 실습을 시작할 때마다 DB에서 확인한다(#6).
- 미정 — 결정 필요: 개인정보 수집·이용 동의 안내 문구(수집 항목, 목적, 보관 기간). 화면(fe)을 만들 때 정한다.
