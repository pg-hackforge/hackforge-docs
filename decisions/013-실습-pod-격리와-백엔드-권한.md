# 013. 실습 Pod 격리와 백엔드 권한

- 상태: 채택
- 날짜: 2026-11-11

## 배경

학습자는 실습 Pod 안에서 root 셸을 가진다. Sysbox와 `hostUsers: false`로 그 root는 노드에서 일반 사용자로 실행되지만([ADR 009](009-sysbox-containerd-설정.md)), 같은 노드에는 다른 학습자의 실습 Pod, 백엔드, DB, control plane이 함께 돈다. 실습 환경 기능(#6)에서 막아야 하는 것은 다음과 같다.

- 실습 Pod에서 외부, API server, kubelet, 다른 세션, 노드로 나가는 통신
- Pod에 들어간 Kubernetes API token 사용
- CPU, 메모리, 프로세스 수, 디스크를 혼자 다 써서 노드 전체를 멈추게 하는 것
- 백엔드 코드를 고치다 `privileged` 같은 위험한 설정이 실습 Pod에 들어가는 것
- 백엔드 인증 정보가 유출됐을 때 클러스터 전체를 조작하는 것

세션 수명 주기와 namespace 단위 격리는 [ADR 012](012-실습-환경-수명-주기.md)에서 정했다.

## 선택지

API token

1. Pod spec에 `automountServiceAccountToken: false`
2. namespace의 `default` service account에 같은 설정
3. 둘 다

CPU, 메모리

1. 백엔드가 Pod spec에 직접 넣음. 값은 설정에서 읽음
2. namespace에 LimitRange로 기본값을 줌
3. 문제마다 값을 다르게 줌

프로세스 수

1. kubelet `podPidsLimit`
2. 제한 없이 메모리 limit에 맡김
3. Sysbox나 containerd에서 따로 설정

namespace 상한

1. ResourceQuota
2. ResourceQuota 없이 Pod 이름을 고정
3. 둘 다

Pod 보안 수준

1. Pod Security Admission `baseline`
2. Pod Security Admission `restricted`
3. 1번에 더해 ValidatingAdmissionPolicy로 `runtimeClassName`, `hostUsers` 검사
4. 검사 없이 백엔드 코드만 믿음

디스크

1. Pod에 `ephemeral-storage` limit, `/var/lib/docker`에 `sizeLimit`이 있는 emptyDir
2. Sysbox 데이터(`/var/lib/sysbox`)를 별도 디스크로 분리
3. 제한 없이 모니터링만

네트워크

1. 백엔드가 namespace마다 NetworkPolicy를 만듦
2. 클러스터 구성 때 Calico GlobalNetworkPolicy를 한 번 적용
3. 둘 다

백엔드 권한

1. RBAC(ClusterRole)만
2. RBAC에 더해 ValidatingAdmissionPolicy로 백엔드가 다룰 수 있는 namespace를 `lab-`로 제한

## 결정

| 항목 | 결정 |
|---|---|
| API token | 1번. Pod spec `automountServiceAccountToken: false` |
| CPU, 메모리 | 1번. requests와 limits를 같게 함 |
| 프로세스 수 | 1번. kubelet `podPidsLimit` |
| namespace 상한 | 3번. ResourceQuota와 Pod 이름 `lab` 고정 |
| Pod 보안 수준 | 1번. `lab-` namespace에 `pod-security.kubernetes.io/enforce: baseline` |
| 디스크 | 1번 |
| 네트워크 | 3번 |
| 백엔드 권한 | 2번 |

### 세션마다 만드는 오브젝트

reconciler가 이 순서로 만든다(ADR 012).

```yaml
kind: Namespace
metadata:
  name: lab-<세션 id>
  labels:
    hackforge/lab: "true"
    pod-security.kubernetes.io/enforce: baseline
---
kind: NetworkPolicy
metadata: { name: deny-all }
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]          # 허용 규칙 없음
---
kind: ResourceQuota
metadata: { name: lab }
spec:
  hard:
    pods: "1"
    requests.cpu: <cpu>
    limits.cpu: <cpu>
    requests.memory: <memory>
    limits.memory: <memory>
    requests.ephemeral-storage: <disk>
---
kind: Pod
metadata: { name: lab }
spec:
  runtimeClassName: sysbox-runc
  hostUsers: false
  automountServiceAccountToken: false
  enableServiceLinks: false
  restartPolicy: Never
  containers:
  - name: lab
    image: <lab_sessions.image>
    imagePullPolicy: IfNotPresent
    resources:
      requests: { cpu: <cpu>, memory: <memory>, ephemeral-storage: <disk> }
      limits:   { cpu: <cpu>, memory: <memory>, ephemeral-storage: <disk> }
    readinessProbe:
      exec: { command: [/hackforge/ready.sh] }
      periodSeconds: 3
    volumeMounts: [{ name: docker, mountPath: /var/lib/docker }]
  volumes:
  - name: docker
    emptyDir: { sizeLimit: <disk> }
```

- `<cpu>`, `<memory>`, `<disk>`는 설정 `hackforge.lab.cpu`, `hackforge.lab.memory`, `hackforge.lab.disk`에서 읽음
- `restartPolicy: Never`: 주 프로세스가 죽으면 Pod는 `Failed`가 되고 reconciler가 재시도하거나 `POD_LOST`로 종료함. 다시 띄워도 이미지를 다시 load해서 학습자의 작업은 남지 않음
- `enableServiceLinks: false`: 클러스터의 Service 주소를 환경 변수로 넣지 않음
- `/var/lib/docker`에 emptyDir을 연결해 inner docker 데이터도 kubelet이 사용량을 세게 함. Sysbox가 자동으로 붙이는 폴더는 kubelet이 세지 않음

### 클러스터 구성 때 한 번 적용하는 것

`infra/`에 manifest를 두고 [cluster-setup.md](../infra/cluster-setup.md)에 적용 단계를 추가한다.

- Calico GlobalNetworkPolicy: `namespaceSelector: hackforge/lab == "true"`인 Pod의 Ingress, Egress를 모두 거절
- kubelet `podPidsLimit`
- 백엔드 service account `hackforge-backend`와 ClusterRole, ClusterRoleBinding
  - namespaces: `get`, `list`, `create`, `delete`
  - pods: `get`, `list`, `create`, `delete`
  - networkpolicies, resourcequotas: `get`, `create`
- ValidatingAdmissionPolicy와 Binding: 요청자가 `hackforge-backend` service account이면 대상 namespace 이름이 `lab-`로 시작해야 함. namespace를 만들 때는 label `hackforge/lab: "true"`도 있어야 함
- `hackforge-backend`는 namespace `hackforge`에 둠(2026-11-12 결정). 운영에서 백엔드와 DB를 올릴 namespace이고, [계정 운영 runbook](../infra/account-operations.md)의 `<NAMESPACE>`도 같은 값

### 백엔드의 클러스터 접속

- 운영: 백엔드 Pod에 자동으로 들어가는 service account token을 client-java가 읽음(in-cluster 설정). 실습 Pod와 달리 백엔드 Pod는 token 자동 주입을 켜 둠
- 개발: Windows에서 `bootRun`하는 백엔드가 `hackforge.lab.kubeconfig` 경로의 kubeconfig를 읽음. kubeadm의 관리자 kubeconfig가 아니라 `hackforge-backend` token으로 만든 kubeconfig를 써서 운영과 같은 권한으로 동작하게 함. 파일은 저장소 밖에 두고 경로만 설정에 적음
- 설정이 비어 있으면 in-cluster 설정을 씀

### 설정값

- 미정(실측 후 결정): `hackforge.lab.cpu`, `memory`, `disk`, `podPidsLimit`. 테스트 문제 이미지로 개발 VM에서 먼저 재고, 운영 값은 운영 서버에서 확인함([ADR 006](006-개발-VM과-운영-서버.md))
- `podPidsLimit`은 노드의 모든 Pod에 걸려서 백엔드(JVM 스레드), DB, Calico가 충분히 들어가는 값이어야 함

## 이유

- token: 백엔드가 만드는 Pod는 하나라 Pod spec 한 줄로 충분함. `default` service account는 namespace 생성 직후 비동기로 만들어져서 2번은 순서 처리가 필요함. NetworkPolicy가 API server로 가는 통신을 막는 것이 1차 방어이고, token 제거는 2차 방어임
- CPU, 메모리: Pod를 만드는 코드가 한 곳이라 직접 넣으면 빠지는 곳이 없음. requests와 limits를 같게 하면 노드가 정원만큼 자원을 미리 확보해서 세션끼리 느려지거나 eviction되지 않음. 자리가 없으면 Pod가 Pending에 머물고 `start-timeout`으로 실패 처리됨. 문제별 값은 무거운 문제가 생기면 #7(Challenge 형식과 첫 문제(SQLi))에서 설정값 위에 덮어쓰는 방식으로 추가함
- 프로세스 수: Pod spec에는 프로세스 수 필드가 없어서 kubelet 설정이 표준 방법임. Pod cgroup에 걸려서 inner docker의 프로세스도 함께 셈. 2번은 작은 프로세스를 수만 개 만들면 메모리 limit보다 노드 PID가 먼저 바닥날 수 있음
- namespace 상한: 학습자는 token이 없고 API server로 나가는 통신도 막혀서, 상한이 막는 것은 주로 백엔드 버그임. Pod 이름을 고정하면 중복 Pod는 `AlreadyExists`로 거절되고, quota는 비용이 작아서 함께 둠. quota에 CPU, 메모리 합계를 걸면 requests와 limits가 빠진 Pod도 거절됨
- Pod 보안 수준: `baseline`은 `privileged`, host namespace, `hostPath`, `hostPort`, 기본값 외 capability 추가를 거절함. Docker-in-Docker가 안 될 때 흔히 `privileged: true`를 넣는데, 학습자가 root 셸을 가진 Pod에 이 실수가 들어가면 노드 전체가 뚫림. Sysbox는 privileged 없이 inner dockerd를 돌리므로 우리 Pod는 `baseline`을 통과함. `restricted`는 container 안의 root 실행과 기본 capability를 막아서 inner dockerd가 돌지 않을 가능성이 큼. 3번이 막는 `runtimeClassName` 누락은 privileged가 없으면 dockerd가 시작하지 못해 시작 실패로 끝나므로 지금은 필요성이 낮음
- 디스크: 학습자가 디스크를 채우면 노드의 etcd, 백엔드, DB가 쓰기에 실패함. 1번은 세션마다 상한을 두는 방법이고, kubelet이 주기적으로 사용량을 재서 넘은 Pod만 eviction함. 2번은 실습 데이터가 가득 차도 OS와 etcd는 지키지만 세션끼리는 영향을 주고 서버 디스크 구성을 바꿔야 함. 3번은 kubelet이 Sysbox 폴더 사용량을 몰라서 다른 Pod를 eviction할 수 있음
- 네트워크: NetworkPolicy는 표준 오브젝트라 CNI를 바꿔도 남음. GlobalNetworkPolicy는 namespace가 생기기 전부터 적용돼서 백엔드가 NetworkPolicy를 빠뜨리거나 Pod를 먼저 만들어도 막힘
- 백엔드 권한: RBAC는 namespace 이름 조건을 걸 수 없어서 namespace 생성, 삭제와 Pod 생성 권한이 클러스터 전체에 걸림. token이 유출되면 `kube-system`을 지우거나 시스템 namespace에 `privileged` Pod를 만들 수 있음. ValidatingAdmissionPolicy는 내장 기능이라 설치할 것이 없고, 적용하면 유출된 token으로도 `lab-` 밖은 다룰 수 없음

## 결과

- 개발 VM에서 실습 Pod 안으로 들어가 다음을 확인하고 runbook에 기록한다.
  - 인터넷, API server(6443), kubelet(10250), 다른 세션의 Pod, 노드 IP로 연결되지 않음
  - fork bomb이 Pod 안에서만 제한되고 백엔드와 다른 세션은 정상
  - 디스크를 채우면 해당 Pod만 eviction됨
- 백엔드 `clusterTest`(개발 VM)로 확인한다. 실습 오브젝트 생성과 삭제, `privileged` Pod 거절(Pod Security Admission), 백엔드 권한으로 `kube-system` 조작 거절(ValidatingAdmissionPolicy).
- 디스크 1번이 개발 VM에서 동작하지 않으면(Sysbox가 emptyDir 연결을 받아들이지 않거나 `hostUsers: false`에서 inner docker가 쓰지 못함) 2번을 다시 검토한다.
- GlobalNetworkPolicy는 Calico 전용이라 CNI를 바꾸면 다시 만든다.
- #8(공격 대상 화면과 웹 터미널)에서 공격 대상 웹 화면을 백엔드 경유로 열면 NetworkPolicy와 GlobalNetworkPolicy 양쪽에 허용 규칙을 추가한다. 웹 터미널은 API server와 kubelet을 거치는 exec라 Pod 네트워크를 쓰지 않는다. 그때 백엔드 권한에 `pods/exec`의 `get`, `create`를 추가한다([ADR 001](001-kubernetes-client-버전.md)).
- 학습자가 Kubernetes API를 직접 쓰는 문제가 생기면 token, quota, 백엔드 권한 결정을 다시 본다.
