# 002. Console 로그인 인증 방식

- 상태: 채택
- 날짜: 2026-10-24 (채택 2026-11-02)

## 배경

플랫폼 Console(브라우저)의 로그인 방식을 정해야 한다. 계정은 자가 가입이나 GitHub·Google 로그인으로 만들고 관리자 승인 후 쓴다. 관리자가 세션을 강제 종료하면 열려 있는 웹 터미널 연결까지 끊어야 한다. v1.1에는 브라우저 외에 tunnel CLI([ADR 004](004-로컬-연결-방식.md))도 지원하는데, CLI는 브라우저 cookie를 쓸 수 없는 클라이언트다.

## 선택지

1. 서버 세션 + cookie (Spring Security 기본)
2. JWT (stateless token)
3. 이중 구성: 플랫폼 로그인은 JWT, 실습 관리는 세션

## 결정

서버 세션 + cookie를 쓰고 CSRF 보호를 켠다. 세션은 처음부터 Spring Session JDBC로 앱 DB에 둔다.

## 이유

- 서버 쪽 세션을 지우면 즉시 무효가 되므로 로그아웃과 중복 로그인 차단을 바로 처리할 수 있음
- JWT는 만료 전까지 무효화가 어렵고, 차단 목록을 두면 결국 서버 상태가 생김
- 백엔드 하나, 클라이언트도 브라우저 하나라 JWT의 장점(여러 서비스에서 독립 검증, cookie를 못 쓰는 클라이언트)을 쓸 곳이 없음
- Spring Security `oauth2Login`은 로그인 상태를 세션에 저장하므로 GitHub·Google 로그인을 붙일 때 추가 연결 코드가 필요 없음
- XSS 실습 대상을 띄우는 플랫폼이라 token을 localStorage에 두면 탈취 위험이 커지고, cookie에 두면 세션과 차이가 없음
- 이중 구성은 무효화 경로가 둘로 갈라짐. "실습 세션"은 인증이 아니라 DB에 저장하는 도메인 상태이기도 함
- Spring Session JDBC는 앱이 쓰는 DB에 테이블 2개만 추가함. 재시작·재배포해도 로그인이 유지되고, 백엔드를 여러 대로 늘려도 바꿀 게 없음(프로세스는 stateless)

## 결과

- 세션 cookie는 `HttpOnly`, `SameSite=Lax`.
- 공격 대상 앱과 웹 IDE는 Console과 다른 도메인에서 서비스한다. 같은 상위 도메인을 쓰면 XSS 문제의 공격 코드가 Console cookie를 건드릴 수 있다.
- FE는 Console과 같은 origin에서 서비스한다. origin이 다르면 CORS와 `SameSite=None` cookie가 필요해지므로 FE 스택을 정할 때 지킨다.
- 승인 상태는 세션에 담지 않고 실습을 시작할 때마다 DB에서 확인해서, 관리자의 승인·거절이 바로 반영되게 한다.
- 로그인 세션 만료와 실습 환경 30분 idle 종료는 따로 관리한다. Spring Session JDBC는 만료 이벤트를 내지 않으므로 idle 종료는 LabSession의 마지막 활동 시각으로 판단한다.
- 세션에는 로그인 정보만 넣는다. 세션 값은 직렬화돼 DB에 저장되므로 클래스 구조가 바뀌면 기존 세션을 못 읽을 수 있다.
- WebSocket frame은 HTTP 세션 idle 시간을 갱신하지 않는다. 터미널 작업 중 만료되지 않도록 입력이 있을 때만 보내는 heartbeat가 필요하다.
- Console과 다른 도메인(IDE, 실습 대상)으로 넘어갈 때는 사용자·실습·만료에 묶인 짧은 1회용 token을 쓴다.
- v1.1 tunnel CLI처럼 브라우저가 아닌 클라이언트에는 전용 token을 추가하고, 브라우저는 계속 세션 cookie를 쓴다. 이 token도 DB에 저장해 바로 지울 수 있게 한다(JWT를 안 쓰는 이유와 같음).
- 개발용 H2를 메모리 모드로 쓰면 재시작할 때 세션도 사라진다. 운영 DB를 정할 때 함께 정리한다.
