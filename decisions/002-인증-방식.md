# 002. Console 로그인 인증 방식

- 상태: 채택
- 날짜: 2026-10-24 (채택 2026-11-02)

## 배경

플랫폼 Console(브라우저)의 로그인 방식을 정해야 한다. 계정은 자가 가입 또는 GitHub·Google 로그인으로 만들고, 관리자 승인 후 쓴다. 관리자가 세션을 강제 종료하면 열려 있는 웹 터미널 연결까지 끊어야 한다. v1.1에는 브라우저와 함께 터널 CLI([ADR 004](004-로컬-연결-방식.md))도 지원한다. CLI는 브라우저 쿠키를 쓸 수 없는 클라이언트다.

## 선택지

1. 서버 세션 + 쿠키 (Spring Security 기본)
2. JWT (stateless 토큰)
3. 이중 구성: 플랫폼 로그인은 JWT, 실습 관리는 세션

## 결정

서버 세션 + 쿠키를 쓰고, CSRF 보호를 켠다. 세션은 처음부터 Spring Session JDBC로 앱 DB에 둔다.

## 이유

- 서버 기록을 지우면 즉시 무효가 된다. 로그아웃과 중복 로그인 차단이 바로 된다.
- JWT는 만료 전까지 무효화가 어렵다. 차단 목록을 두면 결국 서버 상태가 생긴다.
- 백엔드가 하나이고 클라이언트도 브라우저 하나다. JWT의 장점(여러 서비스가 독립적으로 검증, 쿠키를 못 쓰는 클라이언트)을 쓸 곳이 없다.
- Spring Security의 `oauth2Login`은 로그인 상태를 세션에 저장한다. GitHub·Google 로그인을 따로 이어 붙일 코드가 없다.
- 이 플랫폼은 XSS 실습 대상을 띄운다. 토큰을 localStorage에 두면 탈취 위험이 커지고, 쿠키에 두면 세션과 다를 게 없다.
- 이중 구성은 무효화 경로가 둘로 갈라진다. 게다가 "실습 세션"은 인증이 아니라 DB에 저장하는 도메인 상태다.
- Spring Session JDBC는 앱이 어차피 쓰는 DB에 테이블 두 개만 더한다. 재시작·재배포해도 로그인이 유지되고, 백엔드를 여러 대로 늘려도 바꿀 것이 없다. 세션을 외부 저장소에 두므로 프로세스는 stateless가 된다.

## 결과

- 세션 쿠키는 `HttpOnly`, `SameSite=Lax`로 둔다.
- 공격 대상 앱과 웹 IDE는 Console과 다른 도메인에서 서비스한다. 같은 상위 도메인을 쓰면 XSS 문제의 공격 코드가 Console 쿠키를 건드릴 수 있다.
- FE는 Console과 같은 출처(origin)에서 서비스한다. 출처가 다르면 CORS와 `SameSite=None` 쿠키가 필요하다. FE 스택을 정할 때 지킨다.
- 승인 상태는 세션에 담아 두지 않고 실습을 시작할 때마다 DB에서 확인한다. 그래야 관리자의 승인·거절이 바로 반영된다.
- 로그인 세션 만료와 실습 환경의 30분 유휴 종료는 따로 관리한다. Spring Session JDBC는 만료 이벤트를 내지 않으므로, 유휴 종료는 LabSession의 마지막 활동 시각으로 판단한다.
- 세션에는 로그인 정보만 넣는다. 세션 값은 직렬화되어 DB에 저장되므로 클래스 구조가 바뀌면 기존 세션을 못 읽을 수 있다.
- WebSocket 프레임은 HTTP 세션 유휴 시간을 갱신하지 않는다. 터미널 작업 중에 만료되지 않도록, 입력이 있을 때만 보내는 하트비트가 필요하다.
- Console과 다른 도메인(IDE, 실습 대상)으로 넘어갈 때는 사용자·실습·만료에 묶인 단기 1회용 토큰을 쓴다.
- v1.1 터널 CLI처럼 브라우저가 아닌 클라이언트에는 그 클라이언트용 토큰을 추가한다. 브라우저는 계속 세션 쿠키를 쓴다. 이 토큰도 DB에 저장해 바로 지울 수 있게 한다. JWT를 쓰지 않는 이유와 같다.
- 개발용 H2를 메모리 모드로 쓰면 재시작할 때 세션도 사라진다. 운영 DB를 정할 때 함께 정리한다.
