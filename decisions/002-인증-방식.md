# 002. Console 로그인 인증 방식

- 상태: 제안 (사람이 승인하면 "채택"으로 바꾼다)
- 날짜: 2026-10-24

## 배경

플랫폼 Console(브라우저)의 로그인 방식을 정해야 한다. 로그아웃하거나 계정이 정지되면, 열려 있는 웹 터미널 연결까지 끊어야 한다.

## 선택지

1. 서버 세션 + 쿠키 (Spring Security 기본)
2. JWT (stateless 토큰)
3. 이중 구성: 플랫폼 로그인은 JWT, 실습 관리는 세션

## 결정 (제안)

서버 세션 + 쿠키를 쓰고, CSRF 보호를 켠다.

## 이유

- 서버 기록을 지우면 즉시 무효가 된다. 로그아웃, 계정 정지, 중복 로그인 차단이 바로 된다.
- JWT는 만료 전까지 무효화가 어렵다. 차단 목록을 두면 결국 서버 상태가 생긴다.
- 백엔드가 하나이고 클라이언트도 브라우저 하나다. JWT의 장점(여러 서비스가 독립적으로 검증, 쿠키를 못 쓰는 클라이언트)을 쓸 곳이 없다.
- 이 플랫폼은 XSS 실습 대상을 띄운다. 토큰을 localStorage에 두면 탈취 위험이 커지고, 쿠키에 두면 세션과 다를 게 없다.
- 이중 구성은 무효화 경로가 둘로 갈라진다. 게다가 "실습 세션"은 인증이 아니라 DB에 저장하는 도메인 상태다.
- 세션을 외부 저장소에 두면 클라우드 네이티브 원칙(stateless 프로세스)도 만족한다.

## 결과

- 인스턴스를 2개 이상으로 늘리면 Spring Session JDBC로 세션을 DB에 둔다.
- WebSocket 프레임은 HTTP 세션 유휴 시간을 갱신하지 않는다. 터미널 작업 중에 만료되지 않도록, 입력이 있을 때만 보내는 하트비트가 필요하다.
- Console과 다른 도메인(IDE, 실습 대상)으로 넘어갈 때는 사용자·실습·만료에 묶인 단기 1회용 토큰을 따로 검토한다.
- 모바일 앱이나 외부 API가 생기면 그 클라이언트용 토큰만 추가한다.
