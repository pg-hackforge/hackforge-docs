# 023. 공격 검증과 힌트

- 상태: 채택
- 날짜: 2026-11-21

## 배경

#9(공격 검증과 단계별 힌트)에서 플랫폼이 공격 성공을 판정하고, 막히면 공격 힌트를 하나씩 공개한다(product.md 유스케이스 3, 4). 검증 스크립트를 실습 Pod 안에서 exec로 실행하고 exit code로 판정하는 것은 [ADR 014](014-challenge-형식과-등록.md)가 정했다. 학습 단계(공격, 방어)를 어디에 둘지, 검증을 어떻게 요청하고 기록할지, 힌트와 건너뛰기 규칙은 정하지 않았다.

제약은 다음과 같다.

- 검증 스크립트는 60초 안에 끝나야 하고 보통 1초 안에 끝난다(ADR 014). exit code 0이 PASS다
- `lab_sessions.status`는 실습 환경의 수명 주기(생성, 준비, 종료)다([ADR 012](012-실습-환경-수명-주기.md))
- 방어 검증(#11)도 같은 실행 경로와 기록을 쓴다. 방어 검증은 최대 5회다
- 공격 검증은 Target 쪽 증거로만 판정하고 학습자에게는 스크립트 출력의 마지막 줄만 보여 준다(ADR 014)

## 선택지

1. 학습 단계: `lab_sessions.stage` 컬럼을 새로 둔다 / `status`에 `ATTACK_VERIFIED` 같은 값을 더한다
2. 검증 요청: 동기(요청이 스크립트 실행을 기다림) / 비동기(요청은 접수만 하고 결과는 polling)
3. 실행: `LabCluster`가 exec stdin으로 실행(ADR 014)
4. 기록: `verifications` 테이블 / 세션 컬럼에 마지막 결과만
5. 공격 검증 횟수: 제한 없음 / 제한
6. 힌트 기록: 공개한 수만 / 힌트마다 공개 시각
7. 공격 건너뛰기: 힌트 3개를 다 본 뒤에만 / 언제든
8. 방어 단계에서 공격 검증: 막음 / 허용
9. 검증, 힌트, 건너뛰기 요청을 활동으로 셈 / 세지 않음

## 결정

1은 `stage` 컬럼, 2는 비동기, 3은 exec, 4는 `verifications` 테이블, 5는 제한 없음, 6은 힌트마다 공개 시각, 7은 언제든, 8은 허용, 9는 활동으로 셈으로 한다(2026-11-21 사람이 결정).

### 학습 단계

- `lab_sessions.stage`: `ATTACK`(처음) → `DEFENSE`. 공격 검증 PASS나 건너뛰기로 한 번만 넘어가고 되돌아가지 않는다. 초기화(#10)의 "처음부터"가 생기면 그때 다시 정한다
- `lab_sessions.attack_skipped`: 건너뛰었으면 true. 건너뛴 뒤 방어 단계에서 공격 검증이 PASS해도 그대로 둔다(기록에 둘 다 남음)

### 공격 검증

- `POST /api/labs/{id}/attack-verifications`는 `RUNNING` 검증을 만들고 202로 바로 응답한다. 백엔드는 응답 뒤 별도 thread에서 문제의 `attack-check.sh`를 실행하고 결과를 저장한다. 클라이언트는 `GET /api/labs/{id}/verifications/{verificationId}`를 1초 간격으로 polling한다
- 세션이 `READY`일 때만 받는다. 단계는 `ATTACK`, `DEFENSE` 모두 받는다. 방어 단계의 PASS는 단계를 바꾸지 않는다
- 세션마다 한 번에 하나만 실행한다. 공격이든 방어든 `RUNNING` 검증이 있으면 409. DB partial unique index로 막는다
- 결과: exit 0이면 `PASS`, 0이 아니거나 60초를 넘기면 `FAIL`, 플랫폼이 스크립트를 실행하지 못하면(exec 실패) `ERROR`. `ERROR`는 학습자 잘못이 아니므로 다시 시도하라고 안내한다
- 메시지: stdout의 비어 있지 않은 마지막 줄(최대 500자). 60초 초과면 "60초 안에 끝나지 않았어요"
- 백엔드가 실행 중에 재시작하면 `RUNNING`이 남는다. reconciler가 시작한 지 2분이 지난 `RUNNING`을 `ERROR`("서버가 다시 시작돼 결과를 잃었어요")로 바꾼다
- 공격 검증 PASS가 `ATTACK` 단계에서 나오면 같은 transaction에서 `stage`를 `DEFENSE`로 바꾼다
- 횟수 제한은 없다

### 실행

- `LabCluster.runScript(sessionId, script, timeout)`: exec(TTY 없음)로 `sh -c 'cd /app && timeout 60 sh'`에 스크립트 본문을 stdin으로 넘기고, exit code와 stdout을 받는다(ADR 014). 방어 검증(#11)의 `exploit.sh`, `functional-test.sh`도 같은 메서드를 쓴다
- 스크립트는 `challenges` 테이블에서 읽는다

### 기록

- `verifications`: 세션, 종류(`ATTACK`, `DEFENSE`), 상태(`RUNNING`, `PASS`, `FAIL`, `ERROR`), 메시지, 걸린 시간, 시작·끝 시각. 방어 검증의 보안·기능 테스트 결과와 해답 확인 후 여부는 #11에서 컬럼을 더한다
- `GET /api/labs/{id}/verifications`로 그 세션의 검증 기록을 최근 순으로 준다(실습 화면 "기록")

### 힌트

- `lab_session_hints`: 세션, 단계(`ATTACK`, `DEFENSE`), 순서(1~3), 공개 시각. 방어 힌트(#11)도 같은 테이블을 쓴다
- `POST /api/labs/{id}/attack-hints`는 다음 공격 힌트 하나를 공개한다. 1 → 2 → 3 순서이고 다 공개했으면 409. `READY`이고 `ATTACK` 단계일 때만 받는다
- `GET /api/labs/{id}/hints`는 공개한 힌트(내용, 공개 시각)와 단계별 전체 개수를 준다. 단계와 상관없이 이미 공개한 힌트는 계속 볼 수 있다
- 세션 응답에는 `stage`, `attackSkipped`, 공개한 공격 힌트 수를 넣는다

### 건너뛰기

- `POST /api/labs/{id}/attack-skip`은 `READY`이고 `ATTACK` 단계이면 힌트를 몇 개 봤든 `DEFENSE`로 넘기고 `attack_skipped`를 기록한다

### 활동

- 검증, 힌트, 건너뛰기 요청은 `ActivityTracker`로 활동에 넣는다. 검증 결과 polling은 세지 않는다

## 이유

- 1: 실습 환경 상태와 학습 진행은 따로 바뀐다. 한 값에 섞으면 `READY`인지 확인하는 곳마다 단계 값까지 함께 봐야 하고, reconciler가 환경 상태를 바꿀 때 학습 진행이 지워질 수 있다
- 2: 검증이 길어지거나 연결이 끊겨도 결과가 남고, 화면이 진행 상태를 보여 줄 수 있다. 방어 검증(#11)은 스크립트 두 개를 실행해 더 오래 걸리므로 같은 방식이 맞다
- 6: 힌트를 언제 봤는지가 학습 기록(#13)과 문제 난이도 분석에 쓰인다. 공개 수는 행 수로 알 수 있다
- 7: 공격이 아니라 방어를 연습하려는 학습자도 있다. 건너뛴 사실은 기록에 남는다
- 8: 방어 단계에서 고친 뒤에도 공격을 다시 해 보고 판정을 받아 볼 수 있다. 판정 기준은 같고 단계를 바꾸지 않는다
- partial unique index는 동시에 두 요청이 와도 하나만 `RUNNING`이 되게 한다. 앱 코드 검사보다 확실하다
