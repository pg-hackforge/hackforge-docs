# 022. 공격 대상과 웹 터미널 연결

- 상태: 채택
- 날짜: 2026-11-20

## 배경

#8(공격 대상 화면과 웹 터미널)에서 학습자가 브라우저로 자기 실습 Pod의 공격 대상 웹 화면과 터미널을 연다. 실습 화면 배치와 주소창 동작은 [ADR 016](016-fe-디자인-방향.md)이, 접근 확인 순서(로그인 → 학습자 → 세션 → namespace → Pod)는 [ADR 004](004-로컬-연결-방식.md)가 정했다. 백엔드가 Pod에 닿는 방법과 브라우저에 띄우는 방법은 정하지 않았다.

제약은 다음과 같다.

- 실습 Pod는 들어오고 나가는 통신이 모두 막혀 있다([ADR 013](013-실습-pod-격리와-백엔드-권한.md))
- 문제의 서비스는 Pod 안에서 `127.0.0.1:<포트>`로만 열린다. 공격 대상 웹은 모든 문제가 `127.0.0.1:8080`이다(Challenge 템플릿 형식 규칙, [ADR 014](014-challenge-형식과-등록.md))
- 공격 대상 웹은 일부러 취약하게 만든 앱이고 방어 단계에서는 학습자가 코드를 고친다. 플랫폼은 이 앱이 내보내는 HTML, JS, cookie를 통제할 수 없다
- 학습자는 Pod 안에서 root다
- 처음 운영은 학교 연구실 서버이고 도메인과 DNS가 없다. 학습자는 서버 IP로 HTTP 접속한다
- 동시 실습 환경은 30개 정도를 기준으로 한다

## 선택지

백엔드에서 공격 대상 웹으로 가는 경로

1. Kubernetes API의 port-forward로 Pod 안의 `127.0.0.1:8080`에 연결
2. exec로 `nc` 같은 명령을 띄워 중계
3. 백엔드가 Pod IP로 직접 요청(서비스를 `0.0.0.0`에 열고 NetworkPolicy에 허용 규칙)
4. Pod 안 sidecar 프록시
5. API server의 `pods/proxy`, `services/proxy`
6. Ingress controller로 세션마다 주소 발급

공격 대상 화면의 origin

1. 플랫폼과 같은 주소 아래 경로(`/api/labs/{id}/target/...`)
2. 세션마다 하위 도메인(`<무작위>.lab.<도메인>`)
3. 고정 하위 도메인 하나
4. 포트 분리(`http://<서버 IP>:<공격 대상 포트>`)와 gateway의 cookie 정리
5. 서버 IP 두 개와 새 탭
6. iframe `credentialless`(Chrome, Edge만)
7. Pod 안 원격 브라우저 화면 전송
8. 로컬 연결 CLI(ADR 004)를 v1로 앞당김

연결을 하나로 모으는 방법

1. 기능별로 Kubernetes 기능을 쓴다(공격 대상 port-forward, 터미널과 IDE exec)
2. Pod 안에 agent를 두고 포트 하나로 공격 대상, 터미널, 파일을 모두 중계

웹 터미널 재연결

1. 다시 연결하면 새 셸
2. tmux 등으로 이전 셸 유지

## 결정

경로는 1(port-forward), origin은 4(포트 분리와 cookie 정리), 연결 방식은 1(Kubernetes 기능), 재연결은 1(새 셸)로 한다. IDE(#10 방어: 웹 IDE, 재빌드·재배포, 초기화)는 exec 기반 파일 API와 fe 편집기(Monaco)로 하고 agent는 두지 않는다(2026-11-20 사람이 결정).

### 공통 경로

- 브라우저 → 백엔드 → API server → kubelet → 실습 Pod. 공격 대상, 터미널, IDE, v1.1 로컬 연결 CLI가 모두 이 경로를 쓴다
- 백엔드는 매번 로그인 세션의 학습자와 실습 세션을 DB에서 확인하고, 세션이 `READY`일 때만 연결한다
- 실습 Pod로 들어오는 네트워크 통신은 지금처럼 모두 막는다. ADR 013 결과의 "공격 대상을 백엔드 경유로 열면 NetworkPolicy에 허용 규칙을 추가한다"는 하지 않는다

### 권한

- ClusterRole `hackforge-lab-connect`: `pods/portforward`, `pods/exec`의 `get`, `create`(WebSocket 연결은 `get`, SPDY는 `create`)
- 백엔드는 실습 namespace를 만들 때 RoleBinding `lab-connect`(역할 `hackforge-lab-connect`, 대상 `hackforge-backend`)도 만든다. [ADR 021](021-실습-환경-준비-단계.md)의 `lab-log-reader`와 같은 방식이다
- 백엔드 ClusterRole의 `clusterroles` `bind` `resourceNames`에 `hackforge-lab-connect`를 더하고, admission policy는 두 역할 중 하나를 대상 `hackforge-backend`로 묶는 RoleBinding만 허용한다

### 공격 대상 gateway

- 백엔드는 플랫폼 포트와 별도로 공격 대상 포트(`hackforge.lab.target-port`, 개발 8081)를 연다. 이 포트로 온 요청은 경로와 관계없이 모두 공격 대상으로 넘기고, 플랫폼 API는 이 포트에서 응답하지 않는다
- 로그인 확인은 플랫폼 `SESSION` cookie로 한다. cookie는 포트를 구분하지 않아 공격 대상 포트로도 전송된다. 그 학습자의 `READY` 세션을 찾아 그 세션의 Pod로 넘기고, 없으면 안내 페이지를 응답한다
- 공격 대상 포트에서는 플랫폼 CSRF 검사를 하지 않는다. 공격 대상 앱의 폼이 그대로 동작해야 한다
- 공격 대상으로 넘기는 요청
  - 플랫폼 cookie(`SESSION`, `XSRF-TOKEN`)와 `X-XSRF-TOKEN` 헤더를 지운다
  - `Host`는 브라우저가 보낸 값(`<서버 IP>:<공격 대상 포트>`)을 그대로 넘겨, 앱이 만드는 절대 주소가 맞게 한다
- 공격 대상의 응답
  - 플랫폼 cookie 이름으로 심는 `Set-Cookie`를 지운다
  - `X-Frame-Options`를 지우고 `Content-Security-Policy: frame-ancestors <플랫폼 origin>`을 붙여 플랫폼 화면에서만 iframe으로 띄울 수 있게 한다
- 실습이 바뀌면 이전 실습의 cookie를 지운다. gateway가 표시 cookie에 지금 세션 id를 남기고, 값이 다르면 그 요청의 플랫폼 cookie가 아닌 cookie를 모두 만료시키고 빼고 넘긴다
- 요청 하나하나를 활동으로 센다
- port-forward 연결은 세션마다 재사용한다. 요청마다 연결을 새로 열지 않는다
- 공격 대상 앱 안의 WebSocket은 v1에서 중계하지 않는다
- 연결 코드는 `LabCluster` 안에 둔다. 나중에 Pod IP 방식(경로 3)으로 바꿀 때 이 구현만 바꾼다
- 구현은 백엔드 안에서 JDK `HttpClient`로 직접 쓴다(2026-11-20 사람이 결정). port-forward는 kubectl처럼 세션마다 백엔드 안 `127.0.0.1:<빈 포트>`를 열어 Pod로 잇고, 프록시는 그 주소로 요청한다. 대상이 요청마다 세션별로 바뀌고 cookie 규칙이 우리 것이라, Spring Cloud Gateway나 프록시 servlet 라이브러리를 써도 직접 쓰는 코드가 크게 줄지 않는다. nginx, Envoy, Traefik은 port-forward로 Pod에 들어갈 수 없어 Pod IP 방식으로 옮길 때의 후보다
- gateway 코드는 `labsession/gateway` 패키지에 모으고, 백엔드 나머지와는 "로그인한 학습자의 `READY` 세션 찾기"와 "활동 기록" 두 곳으로만 연결한다. 사용자가 많아지면 별도 서비스로 떼어 내고 이 두 곳을 API 호출(forward auth)로 바꾼다. 비슷한 서비스(Gitpod, Eclipse Che 등)는 gateway를 별도 서비스로 두고 Pod 네트워크로 직접 보낸다

### 웹 터미널

- 브라우저와 백엔드는 WebSocket(`/api/labs/{id}/terminal`), 백엔드와 Pod는 exec(TTY)로 연결한다. 셸은 실습 Pod 컨테이너의 `sh`, 작업 폴더 `/app`, root
- 연결할 때 `Origin`이 플랫폼 origin인지 확인한다(Cross-Site WebSocket Hijacking 방지)
- 터미널 크기 변경을 Pod에 전달한다
- 세션당 동시에 3개까지 연다
- 입력은 활동으로 세고, 출력과 연결 유지는 세지 않는다
- 세션이 `READY`가 아니게 되면 서버가 닫고 이유를 알린다. 다시 연결하면 새 셸이다

### 활동 기록

- `ActivityTracker`가 활동 시각을 메모리에 모아 세션당 1분에 한 번 DB에 쓰고, idle 판단은 DB 값과 메모리 값 중 최근 값으로 한다([ADR 012](012-실습-환경-수명-주기.md))

### 운영 도메인

- 미정(결정 필요): 운영 도메인. 도메인과 HTTPS가 생기면 origin을 2(세션마다 하위 도메인)로 옮기고 플랫폼 cookie에 `__Host-` 접두어를 붙인다. `__Host-`는 HTTPS에서만 쓸 수 있다

## 이유

- 경로 1: 지금 격리(들어오는 통신 모두 차단)와 문제 형식을 그대로 쓴다. 개발 PC의 백엔드도 API server만 닿으면 되어 개발과 운영이 같다. 30세션에서 API server가 중계하는 연결은 수십~100여 개이고 실습 Pod 30개의 자원에 비해 작다. 동시 세션이 100개를 넘을 것 같거나 실측에서 API server가 실습 생성과 종료를 늦추면 경로 3(gateway가 Pod IP로)으로 옮긴다
- 경로 2는 요청마다 프로세스를 띄워 느리고, 4~6은 Pod로 들어오는 네트워크 길과 허용 규칙이 필요하다. 5는 경로에 `/api/v1/...`이 붙어 앱의 링크가 깨진다
- origin 4: 포트가 다르면 다른 origin이라 공격 대상 JS가 플랫폼 화면을 읽거나 플랫폼 API 응답을 받을 수 없다. 플랫폼 API의 상태 변경은 `X-XSRF-TOKEN` 헤더가 있어야 하고, 다른 origin에서 헤더를 붙이면 CORS preflight에서 막힌다(플랫폼은 CORS를 허용하지 않음). cookie는 포트를 구분하지 않지만 `SESSION`은 HttpOnly라 공격 대상 JS가 읽거나 덮어쓸 수 없고, 나머지 섞임은 gateway가 정리한다. 브라우저는 포트가 달라도 같은 사이트로 봐서 iframe 안 cookie가 모든 브라우저에서 동작한다. 도메인, DNS, 인증서 없이 연구실 서버에서 동작하고 ticket도 필요 없다
- origin 1은 앱의 `/` 링크가 플랫폼으로 벗어나고, 앱 cookie가 플랫폼 cookie를 덮고, 앱 JS가 플랫폼 권한으로 돈다. 2와 3은 도메인이 있어야 한다. 5는 HTTP에서 다른 사이트 iframe의 cookie가 막혀 패널로 띄울 수 없다. 6은 origin을 바꾸지 않아 포트 분리가 여전히 필요하고, Chrome과 Edge만 지원하며, 새로 고치면 공격 대상 앱 로그인이 사라진다. 7은 세션마다 메모리 수백 MB가 더 들고 학습자가 자기 브라우저의 개발자 도구를 쓸 수 없다. 8은 플랫폼 안 패널이 없고 일정이 늘어난다
- 연결 방식 1: exec는 kubelet이 매번 새로 띄우므로 학습자가 Pod 안을 망가뜨려도 터미널과 IDE가 열린다. agent는 새 언어의 프로그램을 만들어 모든 문제 이미지에 넣어야 하고 학습자가 끌 수 있다. code-server는 메모리를 수백 MB 써서 512Mi Pod에 넣기 어렵다
- 재연결 1: 가장 단순하다. fe가 레일 항목을 오갈 때 터미널을 유지하면 끊기는 경우는 새로 고침과 네트워크 문제 정도다. 불편하면 v1.1에서 이전 셸 유지를 검토한다

## 결과

- 인프라: `infra/k8s/`에 ClusterRole `hackforge-lab-connect`, 백엔드 `bind` 대상 추가, admission policy RoleBinding 규칙 확장. 개발 클러스터에 다시 적용한다
- 먼저 개발 클러스터에서 Sysbox Pod(`hostUsers: false`)의 port-forward와 exec가 되는지, sqlmap 수준의 요청에서 응답 지연과 API server CPU를 잰다. 안 되면 이 ADR을 다시 본다
- 백엔드: 공격 대상 포트와 gateway, 터미널 WebSocket, `ActivityTracker`, `LabCluster`의 RoleBinding과 port-forward·exec. `openapi.yaml` 0.5.0(세션 응답의 공격 대상 주소, 터미널 WebSocket, 공격 대상 포트 동작)
- 운영 서버는 공격 대상 포트도 열어야 한다
- Challenge 형식: 공격 대상 웹은 Pod 안 `127.0.0.1:8080`이라는 규칙을 템플릿 README에 명시한다
- fe 실습 화면(공격 대상 패널, 터미널)은 백엔드가 머지된 뒤 별도 이슈로 만든다
- IDE의 파일 API와 편집 기능은 #10(방어: 웹 IDE, 재빌드·재배포, 초기화)에서 만든다
