# 020. 문제 정보와 목록 API

- 상태: 채택
- 날짜: 2026-11-19

## 배경

[ADR 016](016-fe-디자인-방향.md)은 문제가 수백 개로 늘어나는 것을 기준으로 메인 화면을 정했고, 화면 검토에서 "분류, 난이도, 예상 시간을 문제 정보에 추가하고, 문제 목록 API는 검색, 필터, 정렬, 페이지를 지원한다"고 정했다. 지금 `GET /api/challenges`는 `id`, `slug`, `title`, `description`을 id 순서로 모두 응답한다([ADR 014](014-challenge-형식과-등록.md)). fe 문제 목록 화면을 만들기 전에 문제 정보와 API를 정해야 한다.

제약은 다음과 같다.

- v1 문제는 2~3개지만 문제는 계속 늘어난다
- 문제는 출제자가 Challenge 저장소의 `meta/challenge.env`에 쓰고 `register.sh`가 psql로 등록한다. 등록 API는 없다(ADR 014)
- 내 상태(시작 전, 끝내지 못함, 완료)는 실습 기록이 있어야 알 수 있고, 기록은 #13에서 만든다

## 선택지

찾기(검색, 필터, 정렬, 페이지)

1. 문제 정보만 더하고 fe가 전체 목록을 받아 화면에서 거름
2. 서버가 검색, 필터, 정렬, 페이지를 처리
3. 지금 API 그대로

분류 값

1. 분류 목록을 DB 테이블로 고정하고 문제가 참조
2. 문제마다 자유 문자열
3. 관리자가 화면에서 분류를 관리

## 결정

찾기는 2(서버), 분류는 1(DB 테이블)로 한다(2026-11-19 사람이 결정). fe 화면보다 백엔드를 먼저 만든다.

### 문제 정보

| 정보 | 값 | `challenge.env` |
|---|---|---|
| 분류 | 분류 목록의 키 하나 | `CATEGORY=sqli` |
| 난이도 | 입문, 초급, 중급, 고급 | `DIFFICULTY=INTRO`, `BEGINNER`, `INTERMEDIATE`, `ADVANCED` |
| 예상 시간 | 분 단위 정수(1 이상) | `ESTIMATED_MINUTES=30` |
| 요약 | 목록에 보이는 한 줄, 80자 이내 | `SUMMARY="..."` |

- 설명(`meta/description.md`) 전문은 목록에 넣지 않고 문제 하나를 조회할 때 준다
- 새 문제 표시(NEW)는 처음 등록한 지 14일 안인 문제다. 다시 등록해도 처음 등록 시각(`created_at`)은 바뀌지 않는다
- `register.sh`는 값이 빠졌거나 형식이 틀리면 DB를 바꾸기 전에 거절한다. 목록에 없는 분류 키는 DB FK가 거절하고 등록 transaction 전체가 취소된다

### API

- `GET /api/challenges`
  - 조건: `q`(검색어), `category`(여러 번 가능), `difficulty`(여러 번 가능), `sort`, `page`(1부터)
  - 검색어는 제목, 요약, 분류 이름에서 대소문자 구분 없이 찾는다
  - 같은 조건 안의 여러 값은 "또는", 다른 조건끼리는 "그리고"다
  - 정렬: `NEWEST` 새로 추가된 순(기본), `DIFFICULTY` 난이도 낮은 순, `TIME` 예상 시간 짧은 순. 값이 같으면 새로 추가된 순
  - 한 페이지는 20개다
  - 응답: `items`(문제 목록), `page`, `size`, `totalItems`, `totalPages`, `facets`
  - 문제 항목: `id`, `slug`, `title`, `summary`, `category`(키와 이름), `difficulty`, `estimatedMinutes`, `isNew`
  - `facets`: 분류별 개수와 난이도별 개수. 개수가 0인 항목도 넣는다. 한 조건의 개수는 그 조건을 뺀 나머지 조건(검색어 포함)을 적용해 센다
- `GET /api/challenges/{id}`: 목록의 문제 항목에 `description`(Markdown)을 더해 준다
- 힌트, 해답, 검증 스크립트는 두 API 모두 넣지 않는다(ADR 014와 같음)
- 승인 대기·거절 계정도 조회할 수 있다(ADR 014와 같음)

## 이유

- 서버 처리: 수백 개를 한 번에 받으면 첫 화면이 늦고, 필터별 개수를 화면에서 정확히 세려면 전체를 받아야 한다. 내 상태 필터는 실습 기록과 맞춰야 해서 어차피 서버가 한다. 문제 2~3개로는 확인할 수 없다는 점은 테스트와 mock에 가짜 문제를 넣어 확인한다
- 분류 테이블: "SQL Injection"과 "SQLi"처럼 같은 분류가 표기 차이로 갈라지는 것을 등록 시점에 막는다. 문제가 없는 분류도 필터에 정해진 순서로 보인다. 관리 화면은 지금 규모에 과하다
- 검색은 문자열 포함 검색(ILIKE)으로 한다. 수백 개에서는 충분하고, 느려지면 색인(pg_trgm)을 더한다

## 결과

- 백엔드: migration V8(`challenge_categories`, `challenges`의 `category_key`, `difficulty`, `estimated_minutes`, `summary`), `openapi.yaml` 0.3.0. 목록 응답이 배열에서 페이지 객체로 바뀐다. 지금 이 API를 쓰는 화면이 없어 깨지는 곳은 없다
- Challenge 저장소: template의 `challenge.env` 예시, `register.sh`, README를 고치고 `sqli-login`에 값을 채워 다시 등록한다
- 이미 등록된 문제 행은 migration이 임시 값으로 채우고, 개발 DB에서 `register.sh`로 다시 등록해 실제 값으로 바꾼다
- 내 상태 필터와 칸은 #13에서 실습 기록이 생기면 이 API에 더한다
- fe 문제 목록과 홈 화면은 이 API가 머지된 뒤 별도 이슈로 만든다
