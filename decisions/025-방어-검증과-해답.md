# 025. 방어 검증과 해답

- 상태: 채택
- 날짜: 2026-11-22

## 배경

#11(방어 검증)에서 플랫폼이 학습자의 방어를 판정한다. 기존 공격을 다시 보내고 정상 기능을 시험해서 공격이 모두 막히고 기능이 그대로면 PASS로 실습이 끝난다(product.md 유스케이스 6). 실패가 쌓이면 해답을 보여 준다.

이미 정한 것은 다음과 같다.

- 방어 PASS는 `exploit.sh`가 0이 아니고 `functional-test.sh`가 0인 경우다. `exploit.sh`는 마지막 줄에 아직 통하는 payload를 적는다. 스크립트마다 60초. 최대 방어 검증 시도 횟수는 문제마다 정한다(sqli-login 5회)([ADR 014](014-challenge-형식과-등록.md))
- 검증은 비동기이고 `verifications`에 기록하며, 결과는 polling한다. 방어 검증의 보안·기능 결과와 해답 확인 후 여부는 이 기능에서 컬럼을 더한다([ADR 023](023-공격-검증과-힌트.md))
- 세션마다 검증, 재배포, 초기화 중 하나만 실행한다. 재배포는 학습자가 따로 요청한다([ADR 024](024-방어-IDE-재배포-초기화.md))
- 30분 동안 입력이 없으면 세션을 끝낸다. 25분부터 경고한다([ADR 012](012-실습-환경-수명-주기.md))

## 선택지

1. 판정 순서: 두 스크립트를 항상 둘 다 실행 / 공격이 통하면 기능 테스트를 건너뜀
2. 고친 코드 반영: 검증은 지금 떠 있는 서비스를 시험 / 검증마다 재배포부터
3. 시도 횟수: PASS와 FAIL만 셈 / 요청마다 셈
4. 해답 공개: 최대 횟수만큼 실패하면 열 수 있게 하고 학습자가 열 때 기록 / 바로 보여 줌
5. PASS 뒤 세션: 실습 완료를 기록하고 환경을 둠 / 바로 종료
6. 결과 기록: 두 스크립트의 통과 여부와 마지막 줄, 본 방어 힌트 수, 해답 확인 후 여부 / 여기에 출력 전체도
7. 해답 열기 API: `POST`(열람 기록) / `GET`
8. 결과를 잃은 방어 검증의 시간 기준: 2분 그대로 / 3분

## 결정

1은 둘 다 실행, 2는 떠 있는 서비스를 시험, 3은 PASS와 FAIL만, 4는 열 수 있게 하고 기록, 6은 통과 여부와 마지막 줄, 7은 `POST`, 8은 3분으로 한다. 5는 실습 완료를 기록하고 5분 뒤 종료하되, 그 5분 안에 입력이 있으면 그 뒤로는 평소처럼 30분 기준으로 한다(2026-11-22 사람이 결정. 5는 사람이 제안).

### 방어 검증

- `POST /api/labs/{id}/defense-verifications`는 `RUNNING` 방어 검증을 만들고 202로 바로 응답한다. 결과는 공격 검증과 같은 조회·목록 API로 polling한다
- `READY`이고 `DEFENSE` 단계일 때만 받는다. 검증, 재배포, 초기화 중 하나가 실행 중이면 409
- 실행: `exploit.sh`를 먼저, `functional-test.sh`를 그다음에 각각 60초 제한으로 실행한다. 앞의 결과와 상관없이 둘 다 실행한다
- 보안 테스트 통과: `exploit.sh`가 0이 아님(공격이 모두 막힘). 60초를 넘기면 막혔는지 알 수 없어 통과 아님
- 기능 테스트 통과: `functional-test.sh`가 0. 60초를 넘기면 통과 아님
- 결과: 둘 다 통과면 `PASS`, 하나라도 아니면 `FAIL`, 둘 중 하나라도 실행하지 못하면(exec 실패) `ERROR`
- 검증은 지금 떠 있는 서비스를 시험한다. 고친 코드를 반영하려면 학습자가 먼저 재배포한다. fe는 마지막 재배포 뒤에 IDE에서 저장한 파일이 있으면 "재배포하지 않은 변경이 있어요"라고 알린다
- 결과를 잃은 방어 검증은 reconciler가 3분 뒤 `ERROR`로 바꾼다(스크립트 두 개 120초에 여유). 공격 검증은 2분 그대로. 백엔드가 시작할 때 남은 `RUNNING`을 모두 `ERROR`로 바꾸는 것은 그대로다

### 기록

`verifications`에 방어 검증용 컬럼을 더한다. 공격 검증 행에서는 비어 있다.

- `security_passed`, `functional_passed`: 각 테스트 통과 여부. `ERROR`면 비어 있음
- `security_message`, `functional_message`: 각 스크립트 stdout의 비어 있지 않은 마지막 줄(최대 500자). 아직 통하는 payload와 실패한 기능이 여기 나온다. 60초를 넘기면 "60초 안에 끝나지 않았어요"
- `defense_hints_revealed`: 요청할 때까지 공개한 방어 힌트 수
- `after_solution`: 요청할 때 해답을 이미 열었는지
- `message`: 결과 요약. PASS "공격이 모두 막히고 정상 기능이 동작해요", FAIL은 통과하지 못한 쪽을 적는다("공격이 아직 통해요", "정상 기능이 동작하지 않아요", 둘 다면 둘 다)

스크립트 출력 전체는 남기지 않는다. 출제자가 디버깅용으로 찍은 내용이 섞일 수 있고, 학습자에게 필요한 것은 마지막 줄에 있다(ADR 014).

### 시도 횟수와 해답

- 방어 검증 시도 횟수는 `PASS`와 `FAIL`로 끝난 방어 검증 수다. `ERROR`는 세지 않는다. 세션 컬럼을 따로 두지 않고 `verifications`에서 센다
- 방어 검증 `FAIL`이 문제의 최대 시도 횟수(`max_defense_attempts`)만큼 쌓이면 해답을 열 수 있다. 최대 횟수를 넘어도 방어 검증은 계속 받는다
- `POST /api/labs/{id}/solution`: 열 수 있으면 해답(`challenges.solution`)을 주고, 처음 열 때 `lab_sessions.solution_viewed_at`을 기록한다. 아직 열 수 없으면 409. 단계와 상관없이 `READY`가 아니어도 이미 연 해답은 다시 볼 수 있다(종료한 세션의 기록 화면)
- 해답을 연 뒤의 방어 검증은 `after_solution`이 true다. 그 PASS가 "해답 확인 후 PASS"다
- 세션 응답에 방어 검증 시도 횟수, 최대 횟수, 해답을 열 수 있는지, 해답을 연 시각을 넣는다

### 실습 완료와 종료

- 첫 방어 검증 `PASS`가 끝날 때 같은 transaction에서 `lab_sessions.completed_at`을 기록한다. 그 뒤의 PASS는 바꾸지 않는다
- 완료 뒤에도 실습 환경은 그대로이고 검증, 재배포, 초기화, 공격을 계속할 수 있다
- 완료 뒤 입력이 없으면 5분 뒤 종료한다. 5분 안에 입력(활동)이 있으면 그 뒤로는 평소처럼 마지막 입력에서 30분이다
  - 종료 시각: 마지막 입력이 완료 시각보다 앞이면 `completed_at + 5분`, 뒤면 `last_activity_at + 30분`
  - 완료 뒤 5분 안에 종료되면 종료 사유는 `COMPLETED`, 입력이 있은 뒤 30분 종료는 평소처럼 `IDLE`
  - 경고는 지금처럼 종료 5분 전부터라 완료 직후부터 보인다. fe는 이때 "실습을 완료했어요. 5분 뒤 종료돼요 [계속하기]"로 바꿔 보여 준다
- 세션 응답에 `completedAt`을 넣는다. `idleDeadline`, `idleWarningAt`은 위 종료 시각을 따른다

### 활동

- 방어 검증 요청과 해답 열기는 활동으로 센다. 결과 polling은 세지 않는다(ADR 023)

## 이유

- 1: 결과 화면에 보안과 기능 결과를 둘 다 보여 줘야 학습자가 다음에 무엇을 고칠지 안다. 기능 테스트는 몇 초면 끝난다
- 2: 재배포와 검증을 따로 둔 ADR 024와 맞고, 터미널에서 직접 서비스를 다시 띄운 경우도 그대로 시험한다. 검증마다 빌드하면 빌드 실패가 방어 실패로 섞인다
- 3: 서버 쪽 문제로 학습자의 시도 횟수가 줄면 안 된다
- 4: 끝까지 스스로 풀고 싶은 학습자가 있고, "해답 확인 후"를 실제 열람으로 기록할 수 있다
- 5: 완료한 뒤 바로 지우면 통과한 코드를 다시 보거나 공격을 다시 해 볼 수 없다. 완료한 뒤 그냥 떠난 환경을 30분 동안 두면 정원(개발 2개)을 오래 차지하므로 5분으로 줄이고, 계속 쓰는 학습자는 평소 규칙을 따른다
- 6: 마지막 줄로 학습자에게 필요한 내용이 다 나온다(ADR 014 형식 규칙)
- 7: 열람 기록이 남는 요청이라 안전한 메서드(`GET`)로 두지 않는다
- 8: 방어 검증은 스크립트 두 개라 최대 120초가 걸려, 2분 기준이면 정상 실행을 오류로 바꿀 수 있다

## 결과

- 백엔드: migration V12(`verifications` 방어 검증 컬럼, `lab_sessions.completed_at`, `solution_viewed_at`, 종료 사유 `COMPLETED`), `openapi.yaml` 0.8.0, 방어 검증 실행, 해답 API, 완료 뒤 종료 시각, 세션 응답
- product.md 유스케이스 6과 예외 상황(방어 검증 FAIL, 완료 뒤 종료), LabSession·Verification 개념을 이 결정에 맞춘다
- 방어 검증 clusterTest는 실제 문제의 공격 문자열을 백엔드 저장소(공개 사본이 있음)에 넣지 않도록 테스트용 스크립트로 한다. 실제 sqli-login 확인은 개발 백엔드에서 하고 공격 문자열과 고친 코드는 PR에 적지 않는다
- fe 실습 화면(방어 검증, 결과, 해답, 완료 안내)은 백엔드가 끝난 뒤 별도 이슈로 만든다
