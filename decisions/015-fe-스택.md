# 015. fe 스택

- 상태: 채택
- 날짜: 2026-11-17

## 배경

계정(#12), 실습 환경(#6), 문제 목록(#7)의 백엔드가 끝났고 화면은 모두 fe 스택을 정한 뒤로 미뤄 두었다. #8(공격 대상 화면과 웹 터미널), #10(방어: 웹 IDE, 재빌드·재배포, 초기화)은 화면이 핵심이라 fe 없이는 설계가 어렵다. hackforge-fe 저장소는 빈 상태다.

제약과 조건은 다음과 같다.

- 로그인한 사용자만 쓰는 화면이라 검색 노출이나 서버 렌더링이 필요 없다
- 인증은 서버 세션 cookie(HttpOnly, SameSite=Lax)와 CSRF token(`XSRF-TOKEN` cookie 값을 `X-XSRF-TOKEN` header로)이다([ADR 002](002-인증-방식.md))
- API 타입과 client는 hackforge-be `openapi.yaml`에서 생성하고 손으로 쓰지 않는다(fe `CLAUDE.md`)
- 실습 상태는 몇 초마다 다시 조회해야 하고, 실습 화면에는 상태가 많다(`CREATING`, `READY`, `FAILED`, idle 경고, 정원 초과)
- fe는 사람이 코드를 자세히 리뷰하지 않고 실제 화면을 보고 리뷰한다. 그래서 코드 읽기 쉬움보다 디자인 완성도와 UX를 우선한다(2026-11-17 결정)

## 선택지

1. React + Vite SPA
2. Vue + Vite SPA

3. orval
4. openapi-generator(typescript-fetch)

UI

1. Mantine
2. Tailwind CSS + shadcn/ui
3. MUI

화면 확인

1. mock 모드(MSW)와 실제 백엔드 연결
2. 실제 백엔드 연결만
3. Storybook

`openapi.yaml` 가져오기

1. fe에 복사본을 커밋하고 sync 명령으로 갱신
2. 빌드 때마다 백엔드 main에서 내려받음

## 결정

| 영역 | 결정 |
|---|---|
| 프레임워크 | React + Vite SPA, TypeScript(strict) |
| 연결 | 같은 주소, `/api`는 백엔드. 개발 때는 Vite proxy가 `/api`를 `127.0.0.1:8080`으로 넘김 |
| API | @hey-api/openapi-ts로 타입, SDK 함수, TanStack Query hook 생성. 조회, 캐시, 폴링은 TanStack Query |
| spec | `npm run api:sync`로 `../hackforge-be/openapi.yaml` 복사본과 생성물을 함께 커밋. CI가 생성물과 복사본 일치를 확인 |
| UI | Tailwind CSS v4 + shadcn/ui(바탕 라이브러리는 설치 도구 기본값), 아이콘 lucide, 알림 sonner, 글꼴 Pretendard, 라이트·다크 테마 |
| 라우팅 | React Router |
| 폼 | react-hook-form + zod. 백엔드 `VALIDATION_FAILED`의 `errors[]`를 입력칸별로 표시 |
| 화면 확인 | `npm run dev:mock`(MSW, 시나리오 전환)과 `npm run dev`(실제 백엔드) |
| PR 리뷰 | 확인할 화면 목록과 실행 방법을 PR에 적고 직접 띄워서 봄. 스크린샷은 화면이 많아지면 추가 |
| 테스트 | Vitest + Testing Library(API client, 상태 처리 같은 로직). 브라우저 E2E는 필요해질 때 |
| 품질 도구 | ESLint + Prettier. CI에서 타입 검사, lint, 테스트, 빌드 |
| 실행 환경 | Node 26 LTS, npm |

웹 터미널과 웹 IDE를 붙이는 방식은 이 ADR에서 정하지 않는다. #8, #10에서 백엔드 구조(WebSocket exec, Pod 안 IDE 서버 여부)와 함께 정한다. xterm.js와 Monaco 모두 React에서 쓸 수 있어 이 스택이 그 선택을 막지 않는다.

## 이유

- React는 사용률과 만족도가 모두 높고 자료가 가장 많다. xterm.js, Monaco, OpenAPI 생성 도구가 React 기준으로 가장 잘 갖춰져 있다. Next.js의 서버 렌더링은 이 플랫폼에서 얻는 것이 없고 Node 서버 운영이 늘어난다. Vite는 2026년 3월 Vite 8에서 번들러가 Rolldown으로 바뀌었고 사용률이 webpack과 비슷하며 만족도는 크게 앞선다(State of JS 2025)
- 같은 주소로 두면 지금 cookie와 CSRF 설정이 그대로 동작하고, fe와 be를 따로 배포할 수 있다([ADR 003](003-저장소-분리.md)). jar에 넣으면 fe만 고쳐도 백엔드를 다시 빌드해야 하고, 다른 주소는 `SameSite=None`과 CORS 설정이 늘어난다
- 처음에는 openapi-fetch를 골랐지만, openapi-typescript 관리자가 2025-12-29 2026 로드맵에서 openapi-fetch와 openapi-react-query를 유지보수 모드(업데이트 없음)로 돌린다고 밝혀 hey-api로 바꿨다. hey-api는 활발히 개발 중이고 fetch client의 interceptor 한 곳에서 CSRF header를 넣을 수 있다. orval은 생성 파일이 훨씬 많고, mock 데이터를 무작위로 만들어 지정 상태를 보는 데는 어차피 손으로 쓴 MSW handler가 필요하다
- 디자인 완성도를 우선해 Tailwind CSS + shadcn/ui를 골랐다. 컴포넌트 코드를 저장소에 복사해 세부 모양까지 바꿀 수 있고, 참고할 디자인과 완성된 블록이 가장 많다. Mantine은 기본 모양을 벗어나 꾸미는 데 손이 더 간다. 클래스 이름이 길어 코드가 읽기 어려운 점은 화면으로 리뷰하므로 받아들인다. shadcn/ui는 2026년 7월부터 새 프로젝트의 바탕 라이브러리 기본값을 Radix에서 Base UI로 바꿨고, 기본값을 따른다
- 실습 화면의 드문 상태(FAILED, 정원 초과, idle 경고)는 실제 클러스터로 재현하기 어렵고 매번 70초 넘게 걸린다. mock 모드로 모든 상태를 바로 보고, 최종 확인만 실제 백엔드로 한다
- `openapi.yaml` 복사본을 커밋하면 fe PR diff에 쓰는 API 버전이 보이고, 백엔드가 API를 바꿔도 fe main이 갑자기 깨지지 않는다. product.md의 "spec → 백엔드 → 프론트" 순서와 맞다
- React Router는 다운로드 수가 가장 많다. SPA 전용으로는 TanStack Router의 타입 안전성이 장점이지만, 이 플랫폼은 화면 수가 적고 URL 파라미터가 단순해 이득이 작다
- ESLint + Prettier는 여전히 가장 많이 쓰고, Biome이나 Oxlint로 바꾸기도 쉽다
- Node는 2026-11 기준 Active LTS인 26을 쓴다

## 결과

- hackforge-fe에 Vite + React 프로젝트, CI, `api:sync`, mock 모드, 앱 틀을 만든다([specs/fe-setup/tasks.md](../specs/fe-setup/tasks.md))
- 백엔드는 바꿀 것이 없다
- API가 바뀌면 백엔드 머지 뒤 fe에서 `api:sync` PR을 올린다
- 화면은 기능별 이슈로 만든다. 디자인 방향(톤, 강조 색, 배치)은 첫 화면 이슈에서 정하고, 이번에는 테마 구조와 shadcn/ui 기본 색만 둔다
- 미정(결정 필요): 운영에서 fe 정적 파일을 어디서 서빙할지(nginx, Ingress 등). 운영 서버 구성 때 정한다([ADR 012](012-실습-환경-수명-주기.md)의 운영 항목과 함께)
