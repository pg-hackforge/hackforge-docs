# 003. 저장소를 docs / be / fe 셋으로 나눈다

- 상태: 채택
- 날짜: 2026-11-02

## 배경

설계 판단이 대화와 학습 노트에 흩어져 있었다. AI는 대화가 끝나면 맥락을 잃으므로, 작업할 때마다 다시 읽을 수 있고 변경 이력이 남는 기준 문서가 필요하다. 백엔드와 프론트엔드는 따로 배포한다.

## 선택지

1. 저장소 하나(monorepo)에 문서, 백엔드, 프론트를 모두 둠
2. 저장소 셋(`hackforge-docs`, `hackforge-be`, `hackforge-fe`)으로 나누고 로컬 `code/` 아래에 나란히 clone
3. 설계 문서는 Git 밖 노트에 두고 코드 저장소만 나눔

## 결정

2번을 택하고, 세 저장소를 GitHub Organization 하나 아래에 둔다.

## 이유

- 배포 단위(be, fe)와 저장소 단위가 같음
- 문서도 Git으로 관리하므로 PR 리뷰와 변경 이력이 남음
- `code/`를 열면 AI가 세 저장소의 `CLAUDE.md`, spec, API spec을 함께 읽음
- 3번은 문서 이력이 없고, 코드 저장소만 연 AI는 문서를 못 봄

## 결과

- 저장소 사이의 API spec은 `hackforge-be/openapi.yaml` 하나다. API를 바꿀 때는 spec → 백엔드 → 프론트 순서로 진행한다.
- PR·이슈 템플릿, 라벨, 커밋 규칙을 세 저장소에서 똑같이 유지하는 비용이 생긴다.
- 기능 하나가 여러 저장소에 걸치면 상위 이슈는 docs에, 하위 이슈는 be·fe에 둔다.
