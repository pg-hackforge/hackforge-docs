# 024. 방어: 웹 IDE, 재배포, 초기화

- 상태: 채택
- 날짜: 2026-11-21

## 배경

#10(방어: 웹 IDE, 재빌드·재배포, 초기화)에서 학습자는 방어 단계에서 웹 IDE로 코드를 고치고 서비스를 다시 빌드·배포한다. 망가뜨리면 초기화한다(product.md 유스케이스 5, 7). 방어 힌트도 이 기능에서 공개한다(유스케이스 4).

이미 정한 것은 다음과 같다.

- IDE는 exec 기반 파일 API와 fe 편집기(Monaco)로 하고 agent는 두지 않는다([ADR 022](022-공격-대상과-웹-터미널-연결.md))
- 편집 내용은 자동 저장하고 파일별로 처음 상태로 되돌릴 수 있다. `Dockerfile`, `Dockerfile.base`, `compose.yaml`, `init.sql`은 읽기 전용으로 표시한다. 실습 종료와 초기화는 확인 창을 거치고 공격 단계의 초기화는 확인만 받는다([ADR 016](016-fe-디자인-방향.md))
- 재빌드는 base 이미지 위 소스 `COPY`뿐이라 오프라인으로 몇 초면 끝난다([ADR 014](014-challenge-형식과-등록.md))
- 검증은 비동기이고 세션마다 한 번에 하나다. 힌트는 `lab_session_hints`에 공개 시각과 함께 남긴다([ADR 023](023-공격-검증과-힌트.md))

제약은 다음과 같다.

- Challenge 이미지에는 `/app`(compose 프로젝트 소스)만 있고 고친 뒤에는 원본이 남지 않는다
- 학습자는 Pod 안에서 root라 터미널로 Docker 데몬, 디스크, 어떤 파일이든 망가뜨릴 수 있다
- 판정 스크립트는 DB에 있어 학습자가 바꿀 수 없다

## 선택지

1. 원본 코드: 이미지에 원본 사본을 넣는다 / READY 때 백엔드가 `/app`을 복사해 둔다
2. 초기화: 원본 복원과 `docker compose down -v`·`build`·`up`(서비스 초기화) / Pod 재생성(실습 환경 다시 만들기) / 둘 다
3. 읽기 전용 파일: 백엔드의 파일 이름 규칙 / 문제마다 편집 가능 목록 / 문제마다 수정 불가 목록
4. 저장 충돌: 읽을 때의 해시로 확인 / 마지막 저장이 이김
5. 재배포 요청: 비동기, 빌드 로그 끝부분을 DB에 / 동기 / 로그를 Pod 안 파일로
6. 동시 실행: 검증·재배포·초기화 중 하나만 / 각자
7. IDE와 재배포 단계: 방어 단계만 / 공격 단계도 보기 허용
8. 초기화의 "처음부터": 단계와 건너뜀만 되돌리고 기록은 남김 / 공개한 힌트도 지움
9. 방어 힌트: 공격 힌트와 같은 규칙
10. 활동: 파일 저장, 재배포, 초기화, 방어 힌트를 활동으로 셈

## 결정

1은 이미지에 원본, 2는 둘 다, 3은 문제마다 수정 불가 목록, 4는 해시, 5는 비동기와 DB 로그, 6은 하나만, 7은 방어 단계만, 8은 기록 남김, 9는 같은 규칙, 10은 활동으로 셈으로 한다(2026-11-21 사람이 결정. 2의 "둘 다"와 3의 수정 불가 목록은 사람이 제안).

### 원본 코드

- Challenge 템플릿 Dockerfile에 `COPY app/ /hackforge/original/`을 더한다. 파일별 되돌리기와 서비스 초기화가 이 사본을 쓴다. 늘어나는 크기는 `app/` 소스만큼이다(템플릿 7KB, sqli-login 11KB, 이미지 133MB, 529MB 대비)
- 템플릿, sqli-login, 테스트 문제(`infra/lab-test-challenge`)를 다시 빌드해 노드에 import하고 등록한다

### 읽기 전용 파일

- `challenge.env`에 `READONLY`(`/app` 기준 glob, 빈칸으로 나눔)를 둔다. 예: `READONLY="compose.yaml **/Dockerfile **/Dockerfile.base **.sql"`
- `register.sh`가 `challenges.readonly_paths`에 저장한다. 값이 없으면 위 예시를 기본값으로 쓴다
- 파일 API는 여기에 맞는 파일의 저장과 되돌리기를 거절하고, 목록 응답에 파일마다 `readOnly`를 준다
- IDE에서 실수로 고치지 않게 하는 안내다. 학습자는 터미널로 어떤 파일이든 고칠 수 있다. 판정 스크립트는 DB에 있고, 서비스를 꺼서 공격을 막는 우회는 방어 검증의 정상 기능 테스트가 걸러 낸다

### 파일 API

- 대상은 `/app` 아래 파일이다. 1MB를 넘거나 바이너리(NUL 바이트 포함)인 파일은 목록에는 보이되 열지 않는다
- 목록, 읽기(내용과 SHA-256), 저장(읽을 때의 SHA-256을 함께 보냄), 원본으로 되돌리기. 저장 때 해시가 다르면(터미널에서 바뀜) 409이고 화면이 다시 읽을지 묻는다
- 모두 exec로 한다(`find`, `cat`, stdin으로 쓰기, `cp`). 내용은 base64로 주고받아 문자가 깨지지 않게 한다
- `READY`이고 방어 단계일 때만 받는다. 경로는 정규화한 뒤 `/app` 밖이면 거절한다

### 재배포

- `POST`로 `RUNNING` 재배포를 만들고 202로 응답한다. 응답 뒤 별도 thread에서 `cd /app && docker compose build && docker compose up -d`를 실행하고 모든 서비스가 healthy가 될 때까지(`/hackforge/ready.sh`) 기다린다. 결과는 `SUCCESS`, `FAIL`(빌드·기동 실패나 3분 초과), `ERROR`(exec 실패). 클라이언트는 polling한다
- 빌드 로그(stdout과 stderr) 끝 64KB를 `redeploys.log`에 저장하고 화면에 보여 준다
- `READY`이고 방어 단계일 때만 받는다

### 초기화

- `POST /api/labs/{id}/reset`, 본문 `{"scope": "SERVICES" | "ENVIRONMENT", "keepStage": true | false}`
- `SERVICES`(서비스 초기화, 약 20초): `/app`을 `/hackforge/original`로 되돌리고 `docker compose down -v`, `build`, `up -d`, healthy 대기. DB volume도 새로 만들어 초기 데이터로 돌아간다. 재배포와 같은 방식(비동기, `redeploys`에 종류 `RESET`)으로 기록한다
- `ENVIRONMENT`(실습 환경 다시 만들기, sqli-login 약 70초): 세션을 `CREATING`(준비 단계 `SPACE`, 생성 재시도 0)으로 되돌리고 Pod를 지운다. reconciler가 지금의 생성 흐름대로 새 Pod를 만든다. 그동안 터미널은 닫히고 공격 대상은 준비 중 안내가 된다. Docker 데몬이 멈추거나 디스크가 찼거나 원본 사본을 지운 경우처럼 서비스 초기화로 안 될 때 쓴다
- 화면은 확인 창에서 서비스 초기화를 기본으로 두고 실습 환경 다시 만들기를 따로 고르게 한다. 서비스 초기화가 실패하면 결과 메시지에서 실습 환경 다시 만들기를 안내한다
- `keepStage=false`("처음부터")는 단계를 `ATTACK`, `attack_skipped`를 false로 되돌린다. 검증 기록과 공개한 힌트는 기록으로 남는다. 공격 단계에서는 화면이 선택지 없이 `keepStage=true`로 보낸다
- `READY`일 때 받는다(단계는 상관없음)

### 동시 실행

- 세션마다 검증, 재배포, 서비스 초기화 중 하나만 실행한다. 재배포 중 검증하면 결과가 틀어진다
- `verifications`와 `redeploys` 각각에 세션별 `RUNNING` 하나만 두는 partial unique index를 두고, 새 작업을 만들 때 세션 행을 잠근 뒤 두 테이블 모두에 `RUNNING`이 없는지 확인한다. 실행 중이면 409
- 실습 환경 다시 만들기도 실행 중인 작업이 있으면 409
- 재배포와 초기화도 백엔드 재시작으로 `RUNNING`이 남으면 reconciler가 4분 뒤 `ERROR`로 바꾼다

### 방어 힌트

- `POST /api/labs/{id}/defense-hints`. 공격 힌트와 같은 규칙으로 방어 단계에서 1(방향) → 2(위치) → 3(고치는 방법) 순서로 공개하고 공개 시각을 남긴다

### 활동

- 파일 저장·되돌리기, 재배포, 초기화, 방어 힌트 요청을 활동으로 센다. 파일 목록과 읽기, polling은 세지 않는다

## 이유

- 1: 원본이 이미지에 있으면 언제 되돌려도 같고, 학습자가 먼저 고쳐 원본이 틀어질 일이 없다. 늘어나는 크기는 무시할 만하다
- 2: 서비스 초기화는 빠르고 대부분의 경우를 되돌린다. Pod 안의 Docker나 디스크를 망가뜨린 경우는 Pod 재생성만이 확실하다. 재생성은 이미 있는 생성 흐름을 그대로 써서 새로 만들 것이 적다
- 3: 출제자가 문제의 의도에 맞게 막을 파일을 정한다. 기본값이 있어 값을 적지 않은 문제도 동작한다
- 4: 터미널과 IDE를 같이 쓰므로, 확인 없이 덮어쓰면 터미널에서 고친 내용이 조용히 사라진다
- 5: 빌드는 수 초~수십 초 걸리고 실패 원인을 보여 줘야 한다. 로그를 DB에 두면 Pod가 지워진 뒤에도 기록(#13)에서 볼 수 있다
- 7: 공격 단계에서 소스를 열면 화이트박스 힌트가 된다. 유스케이스 3이 "PASS면 방어 단계(웹 IDE)가 열린다"이다
